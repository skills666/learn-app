# 微服务架构的优缺点是什么？

微服务架构也是一种分布式架构，但分布式架构未必是微服务架构。分布式架构相比单体架构解决了模块耦合度高的问题，把应用拆开了，但拆分粒度比较粗，大部分只拆了应用层、数据库层没拆，而且拆分之后带来的跨服务调用、数据一致性这些问题也没有成熟的解决方案。微服务架构就是在分布式架构基础上，拆分粒度更细，应用拆分、数据库也独立拆分，同时对拆分后产生的问题有了一套成熟的解决方案。

优点是五个：

耦合度低，拆分粒度更细，每个服务职责单一，改一个模块影响范围小。

数据库独立，每个服务有自己的数据库，不会出现一个表被多个模块改来改去的情况。

利于维护和扩展，哪个服务压力大就单独扩哪个，不用整个项目一把梭。

故障隔离，一个服务挂了其他服务照样跑，不会整个系统不可用。

对拆分后产生的问题有成熟的解决方案，比如服务注册发现用 Nacos、远程调用用 OpenFeign、分布式事务用 Seata，不是自己从零摸索。

缺点是三个：

带来了很多额外中间件——Nacos、Gateway、Seata、链路追踪，架构复杂度和运维成本比单体高很多。

学习成本高，团队每个人都要懂整套微服务体系。

小项目没必要，模块少、业务简单的项目硬拆微服务就是过度设计。

补充一点：很多人以为微服务只适合高并发项目，其实不是。模块多、业务复杂、团队大的项目同样适合，方便分工维护扩展。

# 你们微服务是怎么拆分的

按业务功能拆的，一个服务只管一块事：

用户端请求全走 Gateway 网关，统一鉴权路由

用户服务：用户注册登录、个人信息管理

订单服务：订单生命周期、8 种状态流转、状态机

派单服务：四层匹配、抢单、师傅 GPS 位置、定时任务调度

AI 客服服务：基于 LangChain + RAG，对接通义千问大模型 API，SSE 流式输出，会话管理

支付服务：同事负责，处理微信支付回调

评价服务：服务完成后打分，异步更新师傅评分

每个服务有自己的数据库，服务之间通过 OpenFeign 调接口，异步场景走 RabbitMQ。拆分原则就是按功能边界划清楚——订单的不管派单的，派单的不管客服的，各自独立部署互不干扰。

# 说一下微服务的常用组件有哪些？

核心五大组件：

注册中心：所有服务启动时注册上来，互相发现调谁。我们用的 Nacos。

配置中心：配置文件统一管理，改配置不用重启。也用的 Nacos。

负载均衡：从服务列表里选一台机器发请求。用的 LoadBalancer。

远程调用：服务之间互相调接口。用的 OpenFeign，底层是 HTTP 协议。

网关：统一入口，做鉴权、路由、跨域。用的 Gateway。

常见的就是这五种。其他的像 Seata 也是微服务组件，但 RabbitMQ、Redis 这些不是，单体架构也能用。

# 你们项目有多少个微服务？有哪些微服务？你们微服务部署总共用了多少台机器？

七个微服务，5 台机器。

服务列表：Gateway 网关、用户服务、订单服务、派单服务、AI 客服服务、支付服务、评价服务，再加 Nacos、RabbitMQ、Redis、MySQL、ES 这些中间件。

机器分配：五台云服务器，两台跑业务服务（订单、派单、用户、AI 客服用 Docker 部署），一台跑 Gateway 和 Nacos，一台跑 MySQL 和 Redis，一台跑 RabbitMQ、ES 和 XXL-JOB。服务按压力分布，没有做到一服务一机器，但核心服务做了多实例部署保证高可用。
