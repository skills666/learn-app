# JVM

# 介绍一下jvm的内存区域

JVM运行时数据区一共五大块，线程共享两块，线程私有三块；

共享区域

一个是堆，存着所有对象的实例和数组，是GC的重点区域；堆又可以细分新生代和老年代：

新生代又分Eden区存放刚new出来的对象，以及S0/S1两个区域轮流做存活区，存放经历过一次GC还活着的对象，GC时把Eden和其中一个Survivor中活着的对象复制到另一个Survivor。

老年代存放长期存活的对象和大对象。

另一个是方法区，存放类信息的，像版本、字段、方法、常量池、静态变量等；jdk8之前叫永久代，是在堆里的；8之后改为元空间，移到了本地内存里；在本地内存后，默认无上限，通过MaxMetaspaceSize可以设置上限，避免类加载过多撑爆系统内存。

私有区域

虚拟机栈：

每个线程都有一个栈，每个方法执行时创建一个栈帧压入栈顶，方法执行完就出栈；

常见异常和触发条件：

StackOverflowError：递归太深，栈深度超过允许值

OutOfMemoryError：线程太多，无法分配新栈空间

本地方法栈，和虚拟机栈一模一样，不过服务对象不同，虚拟机栈执行Java方法，本地方法栈执行native方法，也就是C、C++写的底层方法。

程序计数器，当前线程正在执行的字节码指令的行号指示器，就是记录着当前执行到哪一行字节码了，线程切回来还能接着跑；分支、循环、跳转、异常处理、线程恢复，都靠它知道执行到哪了。

特点：唯一一个不会OOM的区域，内存占用极小。

# 创建对象一定是在堆区分配空间吗？

不一定，大多数对象确实在堆上创建，但逃逸分析判定对象没有逃逸出方法时，JIT会把它在栈上分配，方法结束会自动回收不用GC。如果可以进一步分解为基本类型，直接用标量替换连对象都不用创建。

补充：如果要实现栈上分配，-XX:+DoEscapeAnalysis 必须是开启状态（JDK 8+ 默认开启）

# 什么是jvm的四大引用？

Java从jdk1.2开始把引用分为四种强度递减的类型，控制对象被GC回收的条件。

引用类型：

强引用：普通对象创建，永不回收，除非赋值null或超出作用域

软引用：会在内存溢出前回收，内存充足才保留

弱引用：下次GC一定回收，不管内存够不够，ThreadLocalMap里的Entry用的就是弱引用，key没有强引用时下次GC自动清掉

虚引用：随时可能回收，get()永远返回null，只能和引用队列联用，对象被回收时收到通知

# 说一下java类加载的阶段

类从.class文件到JVM可用的Class对象，要经历七个阶段。

第一阶段加载：类加载器找到.class文件加载到内存中生成Class对象；

第二阶段验证：验证魔数、元数据、字节码、符号引用四个维度，保证字节码安全性；

第三阶段准备：给静态变量分配内存赋零值，常量直接赋实际值；

第四阶段解析：把符号引用替换成直接引用；

第五阶段初始化：执行clinit方法，给静态变量赋真正的值；

之后进入使用，最后GC回收卸载。

# 说一下什么是双亲委派机制？优点是什么？

双亲委派机制就是类加载器收到加载请求时，先查缓存，加载过就直接返回。没加载过才向上委派给父加载器，直到最顶层的Bootstrap，Bootstrap从rt.jar加载核心类，能加载就加载，不能加载再交回给扩展类加载器。扩展类加载器从jre/lib/ext加载，不能加载再交回给应用类加载器，应用类加载器从classpath加载，还不能加载就抛ClassNotFoundException。

三个类加载器：Bootstrap是C++实现的，负责核心类库；扩展类加载器和应用类加载器是Java实现的。

三个优点：可以避免类被重复加载、保护核心API不会被伪造、保证类的全局唯一性，JDBC和Tomcat因为需要反向访问子加载器的类，破坏了双亲委派机制，用线程上下文类加载器和自定义WebAppClassLoader实现。

# gc root根一般包含哪些？什么样的对象会成为垃圾对象？

GC Root类型：最主要的就是静态变量、活跃的线程和局部变量

垃圾对象就是GC Root通过引用链找不到的对象，java用可达性分析而不是引用计数，因为引用计数解决不了循环引用。不可达的对象如果有finalize方法还可能复活一次，但jdk9废弃了。另外软引用、弱引用、虚引用也会影响回收机制。

# 介绍一下常见的垃圾收集算法和垃圾收集器

垃圾收集算法：

标记-清除（Mark-Sweep）

最基础的算法，先标记所有垃圾对象，再统一清除，简单直接，不需要移动对象，但是效率低，标记和清除都会扫描全堆，产生大量内存碎片，大对象可能分配不下。

标记-复制（Mark-Copy）

解决碎片问题，用空间换时间，把内存分成两块，每次只用一块。GC时把存活对象复制到另一块，原来那块清空。没有碎片，速度快，适合存活率低的场景，但是浪费了一半内存，存活率高的话复制成本很大。新生代用的就是这个思路（Eden+两个Survivor，8:1:1）

标记-整理（Mark-Compact）

解决碎片问题，但不想浪费内存，会先标记垃圾，把存活对象全部搬到另一段，然后清理边界外的内存。没有碎片，不浪费内存，适合存活率高的场景，但是移动对象有开销，STW（全局停顿）时间较长，需要更新所有引用关系。

垃圾收集器：

Serial：

最基础的收集器，单线程，GC时暂停所有用户线程，适合桌面应用、小内存的客户端。

Parallel：

是多线程，吞吐量优先，适合后台计算型、批处理、科学计算；调优-XX：MaxGCPauseMillis 控制最大暂停、-XX：GCTimeRatio 控制吞吐量，jdk8默认的垃圾收集器。

CMS：

核心目标是最短停顿时间，算法是标记-清除，所以会有碎片，适合Web应用、对响应时间敏感的系统；分四个阶段：

初始标记：只标记GC Roots直接关联的对象；会全局停顿，但是很短。

并发标记：沿着引用链追踪，和用户线程一起跑。

重新标记：修正并发标记期间变动的引用；会全局停顿，时间稍长。

并发清除：清理垃圾对象。

标记-清除算法无整理，老年代碎片多了会触发Full GC；并发清除阶段新产生的垃圾，只能等下次GC；并发阶段占CPU资源，CPU核少时影响业务

jdk14已经移除了CMS，被G1取代了。

G1：

jdk9的默认收集器；不再分物理上的新生代/老年代，而是把堆切成很多大小相等的Region，哪块垃圾多就先回收哪块，停顿时间可控，同时回收新生代和部分老年代，回收时存活对象移到另一个Region，整体无碎片，适合大内存对停顿有要求的服务端应用。

# 什么是stw？

STW就是GC执行某些阶段时，暂停所有用户线程，用户请求全卡住，这时候系统对外完全没响应；保证标记和清理期间对象的引用关系不变。不同收集器STW差异很大，Parallel全程停；CMS只在初始标记和重新标记停，并发阶段不停；G1停顿可以控制，能设置200毫秒；STW是通过安全点机制实现的，GC设标志位，每个线程跑到下一个安全点时自己挂起，都挂起后才开始GC；对于阻塞的线程，会放到安全区域，在这个区域内引用关系不会变化，GC 时不用等这些线程走到安全点。

# 介绍一下cms垃圾收集器的各个阶段

CMS收集器的目标是最短的停顿时间，分7个阶段：

一阶段初始标记：标记GC Root直接关联的对象，会STW，但只扫一层，速度快。

二阶段并发标记：沿着引用链一路往下追，标出所有存活的对象，用户线程和GC同时跑，这个阶段最耗时，但不会STW，不会影响用户。

补充：可能有漏标、多标、并发标记期间晋升的对象还没被标。

三阶段并发预清理：并发标记期间被修改的引用记录在卡表，预清理阶段把这些变动再扫一遍，减轻重新标记的压力，不会STW。

四阶段可中止的并发预清理：等着Eden区达到一定占用，触发一次Young GC，为什么要等，因为重新标记要扫整个新生代找晋升老年代的引用，如果新生代对象太多，会先让一次Young GC清理新生代，再开始重新标记。

五阶段重新标记：修正并发标记阶段的漏标，扫描新生代对象和卡表，因为有STW，对象引用不能变动，可以把并发标记时漏掉的全部补标回来。

六阶段并发清除：把没标记的对象全部清除，只清对象不整理，会有碎片，不会STW。

七阶段并发重置：清理标记数据。

# 介绍一下g1垃圾收集器的各个阶段

G1把堆分成大小相等的Region（默认2048个，每个1~32MB），一次GC不是扫全堆，而是选垃圾最多的Region优先回收。

G1垃圾回收器的各个阶段：

一阶段初始标记：借Young GC的STW标记GC Root直接可达的对象，停顿时间极短。

二阶段根区域扫描：扫描Survivor区里指向老年代的对象引用，和应用程序并发执行，会在下次Young GC前完成。

三阶段并发标记：从GC Root出发遍历整个对象图，这个阶段最耗时，与用户线程并发执行；并发标记开始时会给当前对象图拍个快照，标记过程中产生的新对象默认当活对象，并发标记期间引用把某个对象的引用删了，快照也会保留该引用，防止漏标导致活对象被回收。

四阶段最终标记：处理并发标记完成后的快照缓冲区里积攒的变更记录，并发标记期间对象引用存在的变化，会先写进快照队列，最终标记一次性消化。

五阶段筛选回收：会STW，时间可控；G1按垃圾占比排序Region，选垃圾最多的多个Region回收，存活对象拷贝到空闲Region，旧Region释放。这一步只回收部分老年代Region，和Young GC混合执行，不会一次回收全部老年代，分多次混合GC慢慢清理，保证每次STW不超过目标时间。

# 你们项目是用哪一个垃圾收集器？为什么用这个？

我们项目用的G1，因为jdk9开始默认G1是默认垃圾收集器。

因为停顿可控、4G到32G堆范围内表现稳定，相比CMS要调新生代比例、老年代阈值等一大堆参数，G1基本开箱即用。

补充：如果堆小于4G追求吞吐量选Parallel，堆大于32G堆停顿要求很高选ZGC。我们目前堆都在4G~16G，G1最合适。

# System.gc()会立马触发垃圾收集吗？

不会。System.gc() 只是给 JVM 一个建议。而且生产环境一般直接禁止了手动 GC，所以调了也没用。就算没禁止，JVM 也不保证立即执行，只是提高 Full GC 的概率。

# 什么是内存溢出？什么是内存泄漏？

内存溢出：就是内存不够用了，程序申请内存时，剩余内存不够分配，抛出OOM。

内存泄露：就是对象没用了，但GC收不走，占着内存不放，内存泄露久了就会导致内存溢出。

常见的泄露场景：

静态集合持有对象引用。

IO/连接流没关闭，占用本地内存

ThreadLocal没remove，线程池复用线程，导致ThreadLocal里的对象收不走。

匿名内部类隐式持有外部Activity/对象的引用。

注册了监听器但没注销，监听器持有目标对象引用，GC收不走。

# 内存溢出怎么解决？

先看报错信息判断是哪个区域溢出，如果是堆溢出，生产环境一般都配了自动 dump 参数，OOM 时会自动生成快照文件，拿 MAT 分析看谁占的大，常见的有：大集合没清、缓存没设上限、数据库查询一次拉太多数据。解决就是该设上限的设上限，该分页的分页，该及时清理的清理。

元空间溢出，一般是动态代理生成类太多或者有大量反射，调大上限或者排查类加载器有没有泄漏。

# cpu飙高怎么解决？

先用 top 找到占用最高的 Java 进程 pid，再用 top -Hp pid 找到占用最高的线程 tid，线程 ID 转十六进制后用 jstack 搜堆栈找到当前在跑的代码。生产环境推荐 Arthas，thread -n 3 一步到位。定位到代码后分原因解决，常见的有：死循环，修一下循环条件，GC 频繁就用 jstat 看是不是内存泄漏，线程太多缩小线程数查看锁竞争；如果是正则回溯，用预编译Pattern代替String.matches。

# 说一下常用的jvm参数有哪些？

常用 JVM 参数分几类：堆内存参数：-Xms 堆初始大小 -Xmx 堆最大内存 两个值设一样大可以避免扩容时的性能抖动；

元空间参数：-XX:MetaspaceSize 初始容量，-XX:MaxMetaspaceSize 用来设置最大值，必须设上限防服务器内存撑爆；

垃圾收集器参数：-XX:+UseG1GC 使用G1垃圾收集器 搭配 -XX:MaxGCPauseMillis 控制停顿时间；

OOM 排查参数：-XX:+HeapDumpOnOutOfMemoryError 自动 dump，生产必加，配合 -XX:HeapDumpPath 指定 dump 文件位置；

GC 日志参数：JDK8 用 -XX:+PrintGCDetails加 -Xloggc:设置日志输出位置，JDK9+ 用 -Xlog:gc*，生产必须开GC日志，出问题才能回溯；

# 有做过jvm调优吗？

新功能上线后频繁 Full GC，jstat 一看老年代使用率 98%，Full GC 后内存不降，说明是泄漏不是堆内存不够。配置了自动 dump 参数，MAT 分析发现静态 ConcurrentHashMap 里存了 300 万个订单快照没过期，代码里把缓存做成永久存储了。

后面把缓存换成 Caffeine 设最大容量和过期时间。同时把原来用的默认 Parallel 收集器，换成 G1 设了 200ms 停顿目标，上线后 Full GC 从一小时几次降到 0，接口响应时间从 3 秒降到 150 毫秒。

# 说一下final、finally和finalize的区别

三个词长得像，但功能完全不同。

final 是修饰类、方法、变量，修饰类不能被继承，修饰方法子类不能重写，修饰变量只能赋值一次，如果修饰的是引用类型的变量，地址不可变，对象里的内容可以变。

finally是用来配合try-catch使用，保证资源释放，不管有没有捕获到异常都会执行。

finalize是Object方法，GC回收前自动调用，但时间不确定、性能差、可能复活对象，JDK9 已废弃，改用Cleaner。
