# 什么是正排索引？什么是倒排索引？说一下倒排索引的底层原理

正排索引就是文档映射关键词，遍历查看文档包含哪些词汇，就像MySQL的全表扫描，一行一行读取数据再匹配条件。

倒排索引反过来，是词条映射文档，通过关键词直接找到所有包含该词的文档，不用全扫，是ES核心索引结构。

底层原理分三层：

第一层词条字典，把所有文档里的词去重排序存起来，用来快速判断一个词存不存在。text字段会分词拆分词条，keyword字段整体当成单个词条。

第二层倒排列表，每个词条绑定一个有序的文档ID，记录这个词出现在哪些文档里、出现的位置和次数。出现次数用来算相关性得分，位置用来关键词高亮。

第三层跳表，当某个词条对应的文档ID列表很长的时候，链表内置跳表结构。多关键词联合查询求交集时，快速跳过不匹配的ID，加速合并结果。

还有写入和查询流程，写入：文档会根据字段类型分词，词条字典新增词条，同步更新对应倒排列表；索引持久化磁盘，同时加载到内存，查询直接走内存。

查询：用户输入分词，逐个词条查倒排列表得到文档ID集合；多个词条去交集得到候选文档；然后计算文档相关性得分，按分数降序，最后读取完整文档返回。

# 你们用的是什么分词器？说一下ik分词器的两种模式

我们用的是ik分词器，他有两种模式。

第一种是ik_max_word，最细粒度拆分。但精准度相对低，可能搜到不太相关的结果。

第二种是ik_smart，粗粒度拆分，精准度高，用户少打一个字就可能搜不到。

补充：我们搜索服务用的是ik_max_word，优先保证用户能搜到结果，然后按相关性分数排序，分数高的自然排前面。

# 项目中一般用es来做什么？怎么保证es和数据库的一致性？

我们项目里ES主要用在搜索服务。用户打开小程序搜索附近的服务人员，走ES倒排索引查，支持分词匹配和相关性排序，还能按地理位置过滤。

一致性这块，用MQ异步同步方案。数据变更的时候，先更新数据库，更新成功后发一条MQ消息，ES同步服务消费这个消息去更新索引。

再做了一个定时任务兜底，每隔一段时间增量对比数据库和ES的数据，发现不一致就补同步。

# 说一下字符串类型keyword和text的区别，说一下全文搜索查询用的是什么关键字？说一下精准匹配查询用的是什么关键字？

keyword和text 最大的区别就是 keyword 不会被分词，整个字段内容当成一个完整的词条存进倒排索引，适合存订单号、手机号、状态枚举这些需要精确匹配的字段。text 会分词，存入的时候用分词器切成一个个词条再建索引，适合存商品名称、服务描述这些需要全文搜索的字段。

全文搜索用match，match会对输入的内容分词，拆分后去倒排索引匹配词条。

精准匹配用term，term不会分词，直接拿整个去倒排索引里找完全匹配的词条。所以term一般用在keyword字段上，用在text字段上可能查不到预期结果，因为text存的时候已经分词了，完整字符串根本不存在索引里。

# 使用es有没有遇到过什么问题？怎么解决？

ES在集群情况下，用户翻到几十页之后响应变慢。ES的深分页from+size方式，比如查第100页，它会从每个分片取前1000条数据汇总到协调节点再排序截断，翻越深性能越差。后面改用search_after方式，用上一页最后一条的排序值作为游标查下一页，性能稳定，但缺点是不能跳页只能顺序翻。对于用户搜服务人员这种场景，没人会翻到几十页之后，所以体验上没影响。
