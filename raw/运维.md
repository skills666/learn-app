# 你们平常是怎么排查生产问题的？

生产问题我一般会按这个流程：

第一步看监控，判断严重程度，先看接口响应时间、错误率、服务器资源。如果有接口突然500爆了或者响应时间翻了好几倍，马上切过去看。

第二步看日志，ELK或者直接上服务器看按关键词搜，如果是报错，找对应时间段的异常堆栈，大部分问题日志能直接看出来，如果是自己负责的模块怀疑有问题，阿尔萨斯的watch命令可以看入参出参，不重启不埋点，现场就能排查。

第三步按问题分类排查：

CPU飙高阿尔萨斯一条thread -n 3直接列出前三。

OOM就jstat -gc PID 1000看GC频率和老年代占用，如果Full GC后内存不降，可能是内存泄露，生产一般配了自动dump，拿MAT分析大类占多少。

接口慢用SkyWalking调用链找到最慢的一环，是数据库慢就EXPLAIN看执行计划；调第三方慢就考虑异步或熔断；代码循环查库可以考虑合并批量；

补充：如果是刚发布的版本，一定要第一时间回滚，慢慢看日志，别在生产环境硬查。

第四步复盘，问题解决记录问题、原因、还有解决方法。

# xxx集群是你部署的吗？

不好意思，Redis、MySQL、Nacos这些集群都是公司有专门的运维同事负责，不过我了解部署架构，开发环境启动时也配过集群连接。

怎么部署的？

我们是用 Docker Compose 编排的，Jenkins 做 CI/CD，代码合到 release 分支自动构建镜像推镜像仓库，然后部署到测试/预发布环境。生产环境部署由运维负责。

Redis 集群怎么搭的？

Redis 集群一般至少三主三从，每个主节点负责一部分槽位（总共 16384 个槽），客户端根据 CRC16(key) % 16384 定位到对应节点。某个主节点挂了，它的从节点顶上来。我们开发环境就用单机 Redis，通过改配置连不同环境。

MySQL 主从怎么搭的？

主库开 binlog，从库配置 CHANGE MASTER TO 指定主库地址和 binlog 位置，启动 IO 和 SQL 两个线程。开发环境我们配好数据源连接池就行，主库连写数据源，从库连读数据源。

Nacos 集群呢？

Nacos 一般三节点，连同一个 MySQL 做数据持久化，前面挂 Nginx 做负载均衡。开发环境我们就在 application.yml 里配 Nacos 地址就行。

# docker命令你熟悉吗？说一下docker的常用命令，说一下dockerfile的常用命令，docker compose的作用是什么？

熟悉的。

常用命令：

docker images：查看本地有哪些镜像

docker pull：从远程仓库拉取镜像

docker rmi：删除本地镜像

docker push：把本地镜像推送到远程仓库

docker build：打镜像

docker run：把镜像跑起来形成容器

docker ps：查看正在运行的容器，加 -a 可以看全部容器包括已经停掉的

docker stop：停止容器

docker start：启动已停止的容器

docker rm：删除容器。运行中的容器不能直接删，要先 stop 再删，或者加 -f 强制删除

docker exec：进入容器内部

docker logs：查看容器日志，加 -f 实时滚动

Dockerfile常用命令：

FROM：指定基础镜像，必须写，而且放在第一行

ENV：设置环境变量

COPY：复制文件或目录到镜像里

RUN：执行 Linux 命令或者 Shell 脚本

ENTRYPOINT：容器启动时执行的入口命令，比如 Java 程序就是 java -jar

Docker Compose的作用：

项目通常有多个容器Java 应用、MySQL、Redis；一个个手动启停很麻烦。Docker Compose 就是用来批量管理的，用一个配置文件把多个服务定义好，一条命令全部启动、一条命令全部停掉。不过它只能在一台机器上操作，多台机器还得靠 Jenkins 或者 K8s。

大概就这些。
