# 说一下synchronized和ReentrantLock的区别？synchronized可以作用在哪些地方？锁的是什么？说一下synchronized的锁升级？可逆吗？

synchronized是Java关键字，自动加解锁，是非公平锁，锁的范围是整个方法，在代码块中使用时，锁的范围就是代码块内；不支持中断

ReentrantLock是JDK类，需要显式创建，只能手动释放锁，可以更细粒度的控制锁的范围；支持中断，也可以设置公平锁。

synchronized可修饰实例方法（锁this）、静态方法（锁Class对象）、代码块（锁括号里的对象）。

锁升级是为了避免一上来就上重量级锁，首先一开始没人来抢锁，这时候是无锁状态，接下来持续只有同一个线程来获取锁就为转为偏向锁，再然后有多个线程交替来获取锁，这时候会转为轻量级锁；这三种状态都不是真正的同时抢锁。直到有多个线程同时抢锁比较激烈的时候，就会转为重量级锁，也就是切换到内核态获取监控器对象，在这之前，轻量级锁会先尝试自旋多次获取锁，实在不行才会转重量级锁。

# 说一下悲观锁和乐观锁的区别？在mysql中有哪些实现？在java中有哪些实现？什么是aba问题？怎么解决？

悲观锁核心思想是认为别人肯定会改，会先加锁再操作，并发性能低，读写全互斥，有死锁风险。

乐观锁是认为别人大概率不改，先操作，提交时检查版本号，并发性能高，读无锁，写冲突才重试。

在MySQL中悲观锁用for update排他锁，其他事务不能读写；lock in share mode共享锁，其他事务可以读但不能写；乐观锁业务表加version字段，更新时where条件加上版本号，影响行数为0表示版本过期，需要重试或提醒用户。

在java中的实现，悲观锁synchronized和ReentrantLock，乐观锁AtomicInteger/AtomicLong、AtomicReference、LongAdder、StampedLock。

aba是CAS操作时，值从A变成B又变回A，CAS检测是发现值还是A，以为没变过。

用AtomicStampedReference加版本号，每次修改版本号+1，CAS时值和版本号都匹配才更新。

# 行锁和表锁的区别是什么？什么时候会上行锁？什么时候会上表锁？行锁锁的是什么？增删改分别上什么锁？

行锁是锁一行或几行，并发度高，有死锁风险，需要管理每行的锁，开销大；表锁是锁整张表，并发度低，所有写操作都互斥，但没有死锁风险，只记录一把锁，开销也小。

上行锁的条件就是InnoDB存储引擎的基础上，where条件只要有一个是带索引的，就是加行锁，一个都没有就加表锁。

行锁有三种：

Record Lock：锁的是单条索引记录

Gap Lock：锁的是索引记录之间的间隙

Next-Key Lock：锁当前行+前面的间隙

增先加插入意向锁，插入成功后对记录加写锁，删改先扫描加Next-Key Lock解决幻读，匹配后锁降级行锁。

# 什么是死锁？造成死锁的原因是什么？怎么打破死锁？java中怎么定位死锁？mysql中怎么定位死锁？锁一定要支持可重入吗？怎么实现可重入？

两个或多个线程/事务互相拿到对方需要的锁，形成闭环等待就是死锁。

死锁要同时满足互斥、持有并等待、不可剥夺、循环等待四个条件才发生死锁。

打破死锁其实就是打破四要素的一个就行，破坏互斥：用CAS。破坏持有等待：用ReentrantLock，先tryLock拿两个锁，拿不到就全释放。破坏不可剥夺：tryLock设置超时，拿不到就放弃。破坏循环等待：统一加锁顺序，规定必须先拿锁1再拿锁2，不允许交叉。

Java定位死锁：

jstack：jstack<进程ID> 打印出所有线程的堆栈信息，搜索 "deadlock" 关键字就能定位。

还有一些自动化运维监控工具，比如阿里的arthas、Prometheus。

MySQL定位死锁：

SHOW ENGINE INNODB STATUS 查看最近死锁日志

SET GLOBAL innodb_print_all_deadlocks = ON 开启死锁日志记录

SELECT * FROM information_schema.INNODB_LOCK_WAITS 查看当前锁等待

是的，一般锁都要支持可重入特性，如果不支持，可能会产生死锁问题。

实现可重入就是给锁加个计数器，同一个线程进来就+1，出去就-1，减到0就释放。

# 说一下公平锁和非公平锁的区别

公平锁每次获取锁先检查等待队列有没有人排队，有人排队就去排队，频繁切换线程，开销大性能低，但不会饥饿；

非公平锁谁抢到算谁的，新来的线程先抢锁，抢不到再排队，性能高，少了排队检查，但是可能导致排队线程一直饿死；

默认用非公平锁，因为非公平锁允许插队，新线程可以直接抢占刚释放的锁，避免了唤醒排队线程的上下文切换开销，虽然牺牲了公平性，但提升了整体吞吐量。
