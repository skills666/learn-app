# 线程池

# 你在项目中有使用过多线程吗？

有，派单调度里用到了线程池。

原来的流程是支付成功后，MQ消费者同步做匹配。但是高峰期MQ消息堆积的时候，单个消费者匹配时间过长，后面的消息排长队没人处理，用户支付完成半小时还没师傅接单。

后面MQ消费消息只改订单状态，匹配交给定时任务每30秒扫一次派单中的订单。扫出来的多个订单提交给线程池并行匹配，一个订单一个线程。

"核心线程数是根据我们服务部署的机器核数来算的，四个。最大线程设为核心的两倍。队列用的是 Synchronous Queue 不排队，因为派单有时效要求，堆积队列不如直接拒绝交给下次定时重试。"

# 线程池的作用是什么？

线程池的三大作用：

第一是复用线程，频繁创建销毁开销很大，因为JVM要为每个线程分配栈内存（默认1MB），频繁new和GC，CPU都花在创建线程上了；线程池让线程跑完一个任务接着跑下一个，不用反复创建销毁。

第二是能控制并发数，通过核心线程+最大线程+任务队列三层限流，来任务先交给核心线程，核心线程满了就放队列排队，队列也满了再创建临时线程兜底，临时线程还满就执行拒绝策略；防止无限增长把系统搞崩。

统一管理，创建销毁、状态监控、异常处理都交给线程池，不用自己管。

# 线程池有哪些核心参数？

核心参数：

int corePoolSize： 核心线程数

int maximumPoolSize：最大线程数

long keepAliveTime：临时线程空闲存活时间

TimeUnit unit：时间单位

BlockingQueue\ workQueue：工作队列

ThreadFactory threadFactory：线程工厂

RejectedExecutionHandler handler：拒绝策略

补充：任务进来先看核心线程够不够，不够就开新的，核心线程满了就进队列，队列满了还没到最大线程就开临时线程，最大线程也满就触发拒绝策略。

拒绝策略：

AbortPolicy：默认行为，直接抛RejectedExecutionException。

CallerRunsPolicy：让提交任务的线程自己执行，变相限流

DiscardPolicy：直接丢弃，不通知

DiscardOldestPolicy：丢弃队列最老的任务，把新任务塞进去

# 说一下线程池的工作原理

来任务之前核心线程数是0，来一个任务才创建一个核心线程，直到核心线程数到设定值，后来的任务就进入工作队列排队，工作队列满后查看当前线程数是否到达最大线程数，没到就创建临时线程，临时线程执行完任务后会进入空闲状态，超过空闲时间就会被销毁，核心线程默认永远不销毁，除非设置allowCoreThreadTimeOut=true。

# 有哪些类型的线程池？

常见的线程池有五种：

newFixedThreadPool：线程数固定，任务多就排队，无界队列可能导致OOM

newCachedThreadPool：没有核心线程，最大线程数无上限，默认空闲60秒就回收，创建大量线程可能导致OOM。

newSingleThreadExecutor：单线程，任务排队，保证FIFO顺序；任务堆积也可能 OOM。

newScheduledThreadPool：核心线程固定，最大线程数无上限，支持定时任务和周期性任务。

newWorkStealingPool：每个线程都有自己的任务队列，空闲线程会从其他繁忙线程队列的尾部偷任务来执行。

补充：Cached和Scheduled最大线程数无上限，都可能OOM，生产环境必须用ThreadPoolExecutor手动设参数。

# 线程池有哪些拒绝策略？你在项目中用的是哪个拒绝策略？如果既想异步也不想丢任务怎么办？

一共四种拒绝策略：

AbortPolicy：默认的拒绝策略，直接抛异常。

CallerRunsPolicy：让提交任务的线程自己处理这个任务。

DiscardPolicy：直接丢弃任务，不抛异常也不通知。

DiscardOldestPolicy：丢弃队列里最老的任务，把新任务塞进去。

我在项目里不同场景用了不同策略：

派单匹配的线程池用的是 AbortPolicy。被拒的任务抛异常，但订单还在派单中状态，下一次 XXL-JOB 扫描还会再捡起来重新提交，等于自带重试。

AI 客服存会话记录、评价异步更新评分这些线程池用的是 CallerRunsPolicy。这些任务不能丢，丢了对话记录就没了。CallerRunsPolicy 虽然会让调用者线程自己执行一下，但至少不丢任务，还能反向给系统施压，如果频繁触发，说明线程池扛不住了该扩容。

如果既不想丢任务也不想牺牲异步，还可以自定义拒绝策略：任务被拒时写到数据库或 Redis 的待重试列表，起一个定时任务定期捞出来重新提交。

# 你在项目中怎么设置线程池的核心参数？

要根据业务类型分，没有万能公式。

我在项目中配了两个线程池，派单匹配的线程池核心是快，核心数是CPU核数，最大线程是核心的两倍。队列用的是SynchronousQueue，容量为0，不排队。因为派单有时效要求，排长队不如直接拒绝，下次XXL-JOB扫描再重试。拒绝策略是AbortPolicy，SynchronousQueue容量为0本质上也是一种有界队列，不会堆积任务导致OOM。

AI客服核心是不丢任务，属于IO密集型任务，核心线程设CPU核数的两倍，因为线程大部分时间都在等IO。队列用有界队列，防OOM。容量按QPS * 可容忍延迟估算，比如期望每秒100个任务，最多等2秒，就设200。最大线程设核心线程的两倍，队列满的时候临时扩一下，给监控告警留反应时间。拒绝策略用CallerRunsPolicy。临时线程回收看业务波动，波动大设30秒，稳定就60秒。

补充：参数不是一次定死，要监控队列长度、线程活跃数、CPU使用率动态调优。

# execute和submit方法有什么区别？shutdown和shutdownnow方法有什么区别？

execute 和 submit 的区别

execute没有返回值，只能传Runnable，提交后线程池执行，执行完就没了。

submit返回一个Future，能拿到执行结果、能捕获异常，传Runnable和Callable都行。

shutdown 和 shutdownNow 的区别

shutdown后，不会接收新任务，但是在跑的会跑完、队列里排队的也会执行完。

shutdownNow会尝试interrupt打断在跑的任务，队列里没跑的直接返回，不执行了。
