# 你们项目用mq来做什么？

第一个是支付成功后触发派单，支付模块发消息，我收到消息后进入派单中状态。

第二个是订单状态变更时发MQ广播，下游模块消费解耦，比如状态变更成待评价就通知评价模块。

# 说一下rabbitmq有哪些的消息模型？

一共五种模型：

简单模型就是一个生产者一个队列一个消费者。

工作队列是一个队列多个消费者轮询消费

发布订阅是Fanout交换机，消息广播绑定到所有绑定的队列。

路由模式是Direct交换机，按routingkey精确匹配。

主题模式是Topic交换机，routingkey支持通配符。

我们项目主要用Direct交换机，按不同的routingkey路由到不同队列。

# 你们技术选型为什么选择rabbitmq？

首先我们业务对消息可靠性有要求，rabbitMQ有消息持久化、手动ACK、confirm回调这些机制，丢消息风险比较低。第二我们团队之前就用过rabbitMQ，运维也有经验，不用额外学新中间件。

# 怎么保证不丢消息？

三个环节。生产者开启confirm回调，消息到Broker才确认。Broker端队列和消息都持久化。消费者手动ACK，业务处理完再确认。我们项目还有兜底，派单消息丢失定时任务扫描也能补上。

# 什么是消息积压？怎么解决消息积压？

生产者发的速度超过消费者处理的速度，消息越堆越多就是消息积压。

先排查根因：是消费者宕机了、消费逻辑变慢了、还是流量突然涨了。排除故障后，能并行处理的加消费者数量，消费逻辑里的慢操作异步化。如果积压太严重已经影响新消息，先把积压消息转存到数据库让队列恢复，后台再慢慢消化。生产上配积压告警提前发现。

# 什么是幂等问题？哪些地方会产生幂等问题？怎么保证幂等？mq怎么保证不要重复消费消息？页面提交如何做防抖？

幂等就是同一个操作执行一次和执行多次，结果都一样，不会因为重复执行产生副作用。

常见的三个场景：

页面重复提交：用户连点按钮，导致同一个请求发了多次。

MQ重复消费：消费者处理完消息准备ACK的时候挂了或者网络超时，MQ以为没消费成功重新投递，导致同一条消息消费多次。

定时任务重复执行：比如多个实例同时扫同一批数据，可能重复处理。

保证幂等的核心思路就是给每个操作加一个唯一标识，处理前先查有没有处理过；常见的三种方案：

第一种数据库唯一索引，重复插入直接报错，业务层捕获后当成功返回。

第二种Redis分布式锁：用业务唯一编号做key，SETNX加过期时间，抢到锁的才执行，没抢到直接返回。

第三种乐观锁，更新操作携带版本号，只有版本匹配才执行更新。

MQ本身做不到完全不重复投递，所以消费者要做幂等兜底。比如消费者拿到消息后，先查一下这条消息对应的业务记录当前是什么状态。比如消息内容是"把某条记录改成已完成"，消费前先查数据库，如果它已经是完成了，直接 ACK 跳过；没完成就正常处理。

防抖分前后端两层：

前端：按钮点击后立刻置灰或者加loading，1-2秒不让重复点击。

后端：用Redis分布式锁，用唯一token做key，同一个key短时间内的重复请求直接拒绝。

# 什么是生产者发送消息的有序性？怎么保证生产者发送消息的有序性？

生产者发送消息的有序性，就是按ABC的顺序发消息，消费者也必须按ABC的顺序消费，比如先发"创建订单"再发"取消订单"，如果取消先到了，业务就乱了。

保证生产者发送有序我了解的有两种方案：

第一是全局有序，就是单个生产者单线程串行发送，同一类需要有序的消息全部发送到同一个队列，消费者单线程串行消费。缺点是吞吐量极低，只适合强有序、消息量小的业务场景。

第二种是局部有序，不需要全队列有序，只保证同一业务内的消息有序，生产者用业务主键做哈希路由，把同一个业务ID的所有消息固定发送到同一个队列，不同业务ID的消息分散到多个队列。

既满足业务层面的有序需求，又能通过多队列并行提升吞吐量。

# 什么是消费者消费消息的有序性？怎么保证消费者消费消息的有序性？怎么做到既要有序性，又要消费快？

消费者消费消息的有序性，就是按照消息入队的顺序，被消费者依次处理，先入队的先消费。

保证消费者消费消息的有序性，可以用单队列加单消费者，队列里消息本来就是先进先出的，只有一个消费者串行处理，顺序就不会乱，多消费者并行消费一定会乱序。

这是个取舍问题，可以从业务上拆，把强有序要求的消息单独走一个队列，但消费者串行保证有序；不需要有序的消息走多队列多消费者并行。

我了解的就这些。

# 什么样的情况消息会成为死信消息？说一下实现延迟消息的整个流程

有三种情况消息会变成死信：

第一种，消息被消费者拒绝并且不重新入队

第二种，消息TTL过期了

第三种，队列满了被丢弃

延迟消息，需要消息先发到一个普通队列，设TTL过期时间，这个队列不绑定消费者，只配置了死信交换机。消息TTL到期后变成死信，死信交换机按路由规则转发到真正的业务队列，消费者监听业务队列收到消息，就实现了延迟效果。

# 在死信交换机的场景中，如果先后有两条消息几乎同时并发进入队列，并且后进入队列的消息的ttl过期时间比先进入队列的消息的ttl过期时间更短，那么后进入的消息ttl到期后会出队吗？

不会，RabbitMQ判断消息是否过期，不是到了TTL时间就删除，而是只有消息到达队列头部时才会检查；如果第一条消息TTL比较长还没过期，它堵在头部，后面的消息就算TTL到期了也不会被检查到。

补充：可以用延时交换机插件，消息发到交换机之后，不会立刻进队列，而是等延时时间到了才投递。

# 订单超时15分钟未支付改成取消的场景中，当业务队列出现了消息堆积的情况怎么办？

首先搞清楚堆在哪，如果消息还在延时队列里没到期，这是正常等待；如果消息已经到期进了死信队列，消费者吃不完，那就直接加消费者数量并行消费就行了。

# 说一下mq和线程池的区别

MQ 和线程池功能上其实很相似的，都可以做异步解耦处理。但在做技术选型上，最根本的考虑是任务的可靠性。

线程池是 JDK 提供的一个类，运行在 JVM 内存里。万一任务刚提交给线程池，这时候 JVM 挂掉了，任务就丢了。而主流 MQ 都有消息可靠性机制保证消息不丢失。

另外线程池是进程内的，只能在本服务里用，跨服务管不着。MQ 是跨进程跨服务的，生产者和消费者不需要同时在线，做到了真正解耦。

所以如果对任务可靠性有要求的，用 MQ。如果对任务可靠性没有要求，用线程池更合适。毕竟引入 MQ 会带来额外的运维部署开销，线程池只是 JDK 的一个类，开发更快成本更低。
