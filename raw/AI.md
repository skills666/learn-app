# AI

# 什么是 AI 智能体？

就是给大模型配一个身份、一套知识、一套工具，让它能像真人一样完成我提的任务。三个核心：System Prompt 定身份、RAG 给知识、Tool Calling 接外部工具。普通大模型你问什么它答什么，智能体有了这三层之后能查资料、能调接口、能按规矩办事。

# 什么是 AI 幻觉？

AI 幻觉就是大模型"胡说八道"。

当前主流的大模型都是基于 Transformer 架构，是根据概率预测来回答问题，它追求的是语言上的合理性，不是事实上的准确性。

虽然随着算法精进，还有 RAG、Tool Calling、提示词工程和模型微调等手段，幻觉已经减轻很多，但从理论上来说，只要模型是概率生成，就没办法彻底消灭。

# 什么是 SSE 协议？

SSE 是一种基于 HTTP 的服务端单向实时推送给客户端的事件协议，适合 AI 大模型的流式响应场景，实现打字机流式输出效果。它轻量、而且浏览器原生支持、还可以自动重连。主流 AI 开发框架如 Spring AI 和 LangChain 输出默认就支持 SSE，都封装好了。

# 一段完整的系统 Prompt 提示词应该包含哪些部分？

会从七个维度来约束智能体：

① 角色定义 你是持有专业资质的营养师，立场客观、严谨，不扮演医生、心理咨询师或其他职业角色。

② 任务说明 专给为用户提供一日三餐搭配、食材选择及日常食养建议，目标是在安全前提下改善饮食习惯。

③ 行为规范 语气专业、温和、易懂；单次回复控制在 300 字以内；信息不完整或存在歧义时，必须主动反问澄清，不臆测用户意图。

④ 内容限制 严禁涉及医疗诊断、开具处方、推荐药品或非食品类保健品；不得承诺"X天瘦X斤"等疗效；超出营养学范畴的请求一律拒答并引导用户就医。

⑤ 专业知识领域 所有知识严格限定于国家卫健委发布的食养指南，以及平台已审核通过的营养科普文库；禁止使用未经验证的网络资料、个案经验或争议性理论。

⑥ 输出格式要求 采用「结论先行 → 依据支撑 → 实操建议」结构；涉及食谱时必须标注食材精确用量（克/毫升）及禁忌人群；复杂内容分条列举，便于阅读。

⑦ 安全与合规 所有表述须符合《食品安全法》《广告法》对食品及保健食品宣传的相关规定；涉及糖尿病、肾病、孕产妇、婴幼儿等特殊人群时，文末必须追加："以上建议仅供参考，不能替代执业医师或临床营养师面诊。"

# 怎么固定大模型的输出？

只在提示词里写"请输出 JSON"是不够的，大模型还是可能不按你的要求来。还要在提示词里给一个完整示例，说明有哪些字段、每个字段什么意思，再用特殊符号把格式框起来，比如"请一定用 \"\"\"json\"\"\" 这种格式来输出"，这样模型更容易识别。

但就算这样也做不到百分之百。要把大模型当成一个不稳定的外部接口，不能完全信它。代码层面要做好校验，拿到大模型输出先 parse 一下，不是合法的 JSON 让大模型重新生成。如果重试几次还不行，或者大模型服务挂了，就走兜底，返回一个预设好的固定 JSON。

# 在日常的工作学习中，AI 一般能做什么？

日常用 AI 主要做需求分析、数据库设计和接口设计。编码阶段用 AI 快速生成代码、遇到 bug 贴报错信息让它给排查思路。开发效率和解决问题的能力提升明显。

# 说一下造成agent死循环的原因以及解决方案

目标模糊型

造成原因：Agent 不知道做到什么程度算完成，永远在"还不够好"中无限循环。典型表现是不停优化、补充、从不交付。

解决方案：给明确终止条件。一，Prompt 里写死"输出最终答案时以 [DONE] 结尾"，代码层面检测到这个标记就强制结束。二，定义可量化的完成标准，比如"代码通过所有单元测试""报告达到 800 字以上"。三，最大步数兜底，比如最多 20 步，到了强制输出当前结果。

信息饥渴型

造成原因：Agent 每次检索都引出新信息，形成"发现未知→探索未知→又发现新未知"的死循环。

解决方案：给好奇心加笼子。一，维护已查询关键词列表，搜过的词不再搜。二，每次调用前先评估现有信息是否够答。三，限制搜索层级深度，比如只搜一级不深挖。

规则僵化型

造成原因：Agent 死守硬规则（如"必填字段不能为空"），跟现实冲突又没有权限变通，卡在矛盾点上反复尝试。

解决方案：让 Agent 学会例外处理。一，区分硬规则和软规则，软规则在用户明确拒绝后可跳过并记日志。二，同一步骤重试超 N 次自动触发放弃，要么跳过要么上报人工。三，提前预设备选方案，比如"用户不给电话→发邮件验证码"。

状态失忆型

造成原因：上下文窗口有限或被覆盖，关键信息丢失，Agent 被迫重复已完成步骤。

解决方案：给 Agent 配外脑。一，关键状态写外部存储，不从上下文恢复。二，每完成 N 步自动做摘要追加，丢弃早期原文。

工具循环型

造成原因：工具返回空、调用失败、输出被误读、多工具循环依赖。

解决方案：让工具输出不再喂养自己。一，空结果也是有效结果，不要重试。二，工具返回结构化数据。三，失败重试设上限。四，工具之间不互相调，用下沉思路抽共享工具。

# 什么是 RAG？说一下 RAG 的流程，你们项目中知识库一般存储什么数据？

RAG 就是检索增强生成；让大模型先翻资料再回答。直接问大模型它可能瞎编，RAG 给它外挂一个知识库，先搜到相关内容，再把搜到的内容跟用户问题一起喂给它，它照着资料回答就不容易编了。

流程分两步。第一步离线阶段，把文档切块、向量化、存进向量数据库。第二步在线阶段，用户提问后先把问题向量化，去库里面搜最相似的几段，再把这几段拼进 Prompt 发给大模型生成答案。

我们项目知识库存的就是标准操作规范、计价规则、合同条款、保险理赔细则这些业务文档。这些文档类型多、粒度不统一，用户问法也千奇百怪，简单的关键词匹配查不准，所以用语义检索来做。

# 为什么选择 Redis 来存储聊天记录？

也不是非要用Redis，主要是本身已经搭了Redis，缓存和分布式锁都在用，把AI聊天记录也放进去不需要部署其他中间件。加上Redis查询快，List结构做滑动窗口刚好满足需求。目前阶段也够用。后面数据量上来了再转，按需升级就行了。

# 你们是怎么解决上下文 Token 超过大模型限制的问题？

有好几种方案。简单的就是滑动窗口，只保留最近 20 轮，老消息自动丢掉，缺点是有短期记忆问题。也可以用大模型对历史做摘要压缩，但历史太长的话摘要本身也可能超上下文，得分批处理。更高级的是把历史记录向量化存起来，每次只检索跟当前问题相关的片段，类似 RAG 的思路。

我们项目用的是滑动窗口，保留最近20轮对话。因为我们的场景是客服咨询，用户问完问题得到答案就走了，很少有超长对话。滑动窗口足够覆盖，没必要上摘要或向量检索，性价比最高。

# 说一下 Prompt 和（RAG、Tool Calling）的区别

这些都是用来增强大模型能力的，像prompt和RAG的区别：

第一是灵活性，prompt是预设的，要改代码或配置。RAG的知识库存的是文档，运营自己上传更新就行，不需要开发介入，比prompt灵活的多。

第二是上下文占用，主流大模型都有上下文长度限制，如果把所有文档都塞进prompt，上下文会爆炸，而且大部分内容跟当前问题无关。RAG的做法是把用户问题向量化之后去向量数据库搜最相关的几段，拼进prompt，上下文占用少，还精准。

prompt和Tool Calling的区别也类似。不一样的地方在于Tool Calling还能帮我们执行逻辑，比如调订单查状态，返回的结构化数据，而RAG返回的一般是非结构化的文字片段。

# 做 AI 项目的时候，遇到了什么问题？如何解决的？

印象比较深的是 RAG 检索准确率的问题。刚上线时候用户问"深度保洁多少钱"，返回的经常是日常保洁的价格，两种保洁的计价文档内容太像了，向量检索靠语义相似度召回，经常把相似但不正确的文档排在前面。

排查发现是单阶段检索精度不够。后来加了一层 bge-reranker 做精排，初检先从 Milvus 召回几条候选，再让 reranker 模型做二次打分，它不是只看语义相似度，是专门评估文档跟问题到底有没有因果关系。上线之后回答准确率明显改善。

# 你们开发完这个 AI 智能助手（AI 智能客服）之后，有没有调查过或者检验过使用情况和精确度如何？

有的。上线后主要看两方面。

一个是覆盖率；后台统计了用户问题中有多少是 AI 直接回答的、多少转人工了。刚上线时覆盖率大概 70% 左右，后面优化了几轮知识库文档和 Prompt，涨到了 80% 以上。转人工的主要是投诉纠纷和特殊理赔——这些本来就不是 AI 该答的，所以 80% 基本达到了预期。

另一个是准确性；定期抽一批 AI 的回答人工复查。早期主要问题是"相似文档召回不准"，比如用户问的是深度保洁，结果喂给大模型的是日常保洁的内容，答偏了。这也是后面加 bge-reranker 精排的直接原因。加完精排之后，抽查的准确率从大概 75% 提到了 90% 以上。

# 什么是 Tool Calling？说一下 Tool Calling 的流程

什么是tool calling？

tool calling（function calling）是大模型通过调用外部工具或API，来完成大模型自身无法直接处理任务的一种机制

说一下tool calling的流程

首先不是所有的大模型都支持tool calling，所以我们得先提前识别哪些大模型支持，然后提前做好工具的定义，一般包含工具的名称、工具的描述和工具的输入参数这几部分组成，接下来可以开始请求大模型，tool calling的过程分为两次请求大模型，第一次请求是把工具连同所有的提示词一起给大模型，然后大模型来识别要不要调用工具，用什么入参，返回给ai应用，ai应用开始调用这些工具，比如调订单服务，就发一个 HTTP 请求过去，拿到返回的 JSON。然后把返回数据拼进上下文，再请求一次大模型，让它基于数据生成自然语言回答。

# Tool 过多，如何提供命中率？

三个策略。

第一是按场景分组，不要把全部工具一次性发给大模型。每次只给和当前场景相关的工具，命中率会明显提高。

第二是工具描述要写清楚，每个工具不仅写名称和参数，还要写什么情况下该用这个、什么情况不该用。大模型是靠文字理解来判断的，描述越明确，选错的可能性就越小，

第三是加一个轻量级路由，在请求大模型之前先用规则或小模型判断用户意图，根据意图决定给哪些工具，而不是把所有判断压力都交给大模型。

# 说一下 Tool Calling 和 RAG 的区别

都是扩展大模型能力，但干的事情不一样。

RAG是给它查资料，从知识库搜相关文档片段，喂给大模型让它照着回答，返回的是非结构化的文字。

Tool Calling是给它调接口，大模型判断需要调哪个工具、填什么参数，你的代码去执行，拿到的是结构化的数据，回来再让大模型润色。

# 什么是 MCP？说一下 MCP 的流程？

了解过原理，但我项目里的 Tool Calling 是直接用 LangChain 原生方式调的，没走 MCP 协议，因为我们工具数量不多，没必要上协议层。

# 说一下 MCP 和 Tool Calling 的区别

MCP 了解过基本概念，它是一套标准化协议，让 AI 应用用统一的方式对接外部工具，不用每个工具都单独适配。但我们项目里没用过 MCP，因为我们工具数量不多，直接走的 LangChain 原生 Tool Calling，没必要上协议层。

# 什么是 Skills？Skills 的本质是什么？什么是渐进式披露？

Skills 就是一种把 AI 的作业流程写成独立文件的标准。以前我们要把所有场景的规则塞进一大段 Prompt，臃肿、难维护、浪费 token。Skills 把每个场景拆成单独文件，AI 按需加载，用哪个就翻哪个。增删任务只需要操作对应文件，不需要动 Prompt。这种按需加载就是渐进式披露，能省 60% 以上的 token。

# 说一下 Skills 的组成部分

一个skill最核心的是skill的md文件，里面两块必填：元数据，写清楚这个技能叫啥、干嘛用的，大模型靠这个判断什么时候该用它；指令，固化好的作业流程，相当于这个小技能专属的系统提示词。其他的像参考文档、执行脚本是可选的，有需要才加。

# 说一下 Skills 的实现原理

Skills 的实现底层就是提示词加工具的组合。AI 拿到用户问题，把问题和所有 Skill 的元数据发给大模型。大模型判断要用哪个 Skill，匹配上了就触发回调。然后加载匹配到的那个 Skill 的完整指令到上下文，大模型按照指令里写好的流程执行。执行过程中如果要查文档或者跑脚本，Skills 规范内置了对应工具，读资源的工具、执行脚本的工具，直接用就行，不用自己写。

# 说一下 Skills 的执行流程

用户提问后，AI扫所有的skill元数据，匹配到最合适的，然后加载那个skill的指令，按指令的流程执行，中间该查文档就调读资源工具、该跑脚本就执行脚本工具，执行完返回结果给用户。

# Skills 和工具的区别是什么？

skills是完整的工作流，一个skill里面可以有多个步骤、引用文档、调工具。它告诉大模型这个场景要先做什么再做什么，什么情况要查什么文档。

工具是单个功能，输入参数，做一件事，返回结果。查订单、查价格、发短信，每个都算一个独立工具。

# Skills 过多，如何提高命中率？

三个策略。

第一按场景分组，不把所有 Skill 一次性堆给大模型。

第二， Skill 名字和描述要写得够清晰，每个 Skill 的元数据要把"什么情况下该用、什么情况下不该用"写清楚，大模型靠文字判断，描述越清楚命中率越高。

第三是加一个轻量级路由层，用户问题进来先做意图识别，根据意图决定给哪组 Skill，而不是把判断压力全交给大模型。

# 怎么解决 Skills 安全性问题？

Skills 一般是外部下载的，存在安全风险。解决方案三个：

第一，严格审查来源和源码，只从官方或可信渠道下载，安装前先过一眼代码。

第二，遵循最小权限原则，工具运行时 AI 拥有当前用户权限，高危操作保持警惕，不盲目点"始终允许"。

第三，不可信的 Skills 在隔离环境或沙箱里跑，比如 Docker 容器只挂必要目录，限制网络和系统调用权限。

# 你们的 AI 智能体是怎么开发的？

用 Python + LangChain 搭的。整体是一条 RAG 流水线，知识库文档用 BGE-M3 做了向量化存进 Milvus，用户提问的时候先搜再答，粗排从 Milvus 召回几条，bge-reranker 精排挑最准的，喂给大模型生成回答。AI 客服单独部署成一个服务，注册到 Nacos 上，前端通过网关直接调它。

# 为什么选择 Spring AI？

我没用 Spring AI。我们 AI 客服选的是 Python + LangChain，因为大模型生态 Python 比 Java 要成熟很多，LangChain 的 RAG、向量检索、Agent 这些能力 Python 社区方案最全。不过 Spring AI 我了解过，如果团队全是 Java 技术栈、不想引入 Python，用它快速对接大模型也是个选择。

# Spring AI 与 Spring AI Alibaba 有什么区别？

Spring AI是由Spring官方牵头的统一的AI接入框架，支持世界上主流大模型平台，但目前对国内支持一般，只能针对支持 openai 接口规范的大模型平台才可以使用，但是比如某些大模型平台的深度功能可能支持不好

Spring AI alibaba 是阿里专门为接入百炼平台大模型在Spring AI基础上做的适配与扩展，能够深度支持阿里百炼平台大模型的深度功能，但是不支持其他大模型平台

# 为什么选择阿里百炼公有大模型，不选择私有部署？

首先我们项目对数据安全性和隐私性没有特殊要求，也没有模型微调的需求。选百炼主要考量是成本，公有云是按量付费的，不需要承担 GPU 服务器和模型运维成本。通义千问 qwen-plus 的能力完全覆盖我们的业务场景，上下文支持 1M，也支持 Tool Calling，目前够用。以后业务复杂度上来了、需要针对特定场景微调，再考虑私有部署。

# AI 模块中具体哪一块是你负责的？

整个 AI 客服模块都是我负责的，从搭环境到上线。具体包括 RAG 流水线的搭建，文档切分、BGE-M3 向量化、Milvus 存储、两阶段检索加精排，到 FastAPI 起服务注册 Nacos，再到 SSE 流式输出对接前端。知识库文档内容是甲方那边运营上传的，我这边只管流水线本身不出问题。

# 什么是 Harness 工程？

Harness工程也叫做驾驭工程，通过搭建统一的运行环境、约束规则和自动校验机制，让系统在固定边界里稳定、重复地跑并自动查错；简单说就是你负责干活，Harness负责管住边界、兜底验证、防止翻车。
