# 说一下数据库的三范式和反三范式

第一范式：每个字段不可再拆分，保证原子性。比如地址不能把省市区塞一个字段里。

第二范式：在第一范式的基础上，非主键字段必须完全依赖主键。比如订单表里放商品名称，商品名称只依赖商品ID不依赖订单ID，就该拆出去。

第三范式：在第二范式的基础上，非主键字段不能有传递依赖。比如学生表里放院系名称，院系名称依赖院系ID，院系ID依赖学生ID，就该拆出去单独一张表。

反三范式：就是为了性能故意违反范式，通过引入冗余数据或合并表结构等手段，优化查询性能，但是不易于维护和保证数据一致性。

# sql的书写顺序是什么？执行顺序又是什么？

书写顺序：SELECT-DISTINCT-FROM-JOIN-ON-WHERE-GROUP BY-HAVING-ORDER BY-LIMIT

执行顺序：FROM-JOIN-WHERE-GROUP BY-HAVING-SELECT-ORDER BY-LIMIT

书写顺序是 SELECT → FROM → JOIN → ON → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT。执行顺序是 FROM + JOIN 先拼表，然后 ON → WHERE 过滤行，再 GROUP BY 分组 → HAVING 过滤组，然后执行 SELECT 算表达式挑列，接着 DISTINCT 去重，最后 ORDER BY 排序和 LIMIT 截断。顺序不一样是因为数据库必须先确定数据来源和行，才能算 SELECT 里的表达式和别名。

# 内连接和外连接有什么区别？内连接和外连接的连接条件能放在on和where吗？

内连接只返回两表都匹配的行，取交集。外连接保留主表全部行，从表匹配不上填 NULL。

内连接 ON 和 WHERE 效果一样，都是只保留匹配行。外连接 ON 是连接条件，决定怎么匹配；WHERE 是连接后的筛选，如果从表条件写在 WHERE 里，不匹配的 NULL 行会被过滤掉，退化成内连接。

# char和varchar的区别

char是定长字符串，存多少都占满，适合固定长度如手机号、身份证号，读写快因为不用算长度。

varchar变长，存多少占多少，最大不超过指定范围，适合不固定长度如姓名、地址，省空间但略慢。

# date、timestamp和datetime的区别

date只有日期，格式是YYYY-MM-DD。

datetime是日期加时间，格式是YYYY-MM-DD HH:MM:SS，范围从1000年到9999年。

timestamp也是日期加时间，但范围是1970年到2038年，存的是UTC时间戳，查询时会自动转成当前时区显示，还会受MySQL时区设置影响；另外timestamp占4字节，datetime占8字节。

# 什么是事务？你说一下事务有哪些特性？

事务是一组要么全成功要么全失败的数据库操作。

四大特性 ACID：

原子性：事务最小的执行单位，要么全成功要么全失败

一致性：事务执行前后，数据必须从一个合法状态变成另一个合法状态，不会出现中间状态和异常数据

隔离性：多个事务并发执行时，事物之间互相隔离，隔离程度取决于隔离级别

持久性：事务提交或回滚，对数据库的改变是永久的

# 说一下事务的隔离级别有哪些？分别解决了什么问题？那脏读、不可重复读和幻读分别是什么？mysql和oracle分别是什么隔离级别？既然读已提交和可重复读分别都还有未解决的问题，为什么成熟的商业数据库mysql和oracle还是选择它们作为默认的隔离级别呢？

隔离级别

读未提交：什么都没解决，会出现脏读、不可重复读、幻读

读已提交：解决了脏读，但还有不可重复读、幻读

可重复读：解决脏读和不可重复读，但还有幻读

串行化：全部解决，但性能最差，事务排队执行

问题

脏读：一个事务读到了另一个事务还没提交的数据，对方回滚了，你读的就是脏数据。

不可重复读：同一个事务多次读同一行，中间被别人改了，多次查询的结果不一样。

幻读：同一个事务里多次查同一个范围的数据，中间被其他事务插了新行，多次查询的结果不一样。

MySQL默认隔离级别是可重复读：因为InnoDB在可重复读级别下通过MVCC和行锁还有间隙锁基本解决了幻读，性能和安全性平衡得最好。

Oracle默认隔离级别是读已提交：因为Oracle认为大多数场景下不可重复读可以接受，业务上用乐观锁或版本号就能处理，没必要为了禁止不可重复读牺牲并发性能。

# 在项目中是怎么做事务控制的？@Transactional事务注解有哪些属性？

主流做法就是在Service层方法上加@Transactional声明式事务注解，AOP自动管理提交和回滚，默认只对运行时异常回滚，项目里一般设rollbackFor=（全部异常类型）Exception.class，涉及多个Mapper的操作放在同一事务里保证原子性。

常用属性：

propagation设置事务传播行为，默认REQUIRED有事务就加入，没有就新建；REQUIRES_NEW不管有没有都会新建独立事务；

isolation设置隔离级别默认用数据库的；

timeout设置超时时间，事务执行太久自动回滚，防死锁；

read-only只读事务，查询方法加上，数据库可以做优化；

rollbackFor指定回滚异常类型。

# 事务失效有哪些场景？

最常见的有：

方法不是public，AOP只对public方法生效；

同类方法A调用方法B，内部调用绕过了代理；

方法里的try catch把异常吞了，Spring感知不到异常就不会回滚；

抛出了非运行时异常，默认只回滚RuntimeException；

数据库引擎不支持，MySQL用MyISAM不支持事务；

# spring的事务的传播行为有哪些？requires_new传播行为一般有什么使用场景？

Spring事务的传播行为一共有七个，我只用过两种：

REQUIRED：默认，有事务就加入，没有就新建

REQUIRES_NEW：不管有没有事务，都新建独立事务，外层事务挂起

REQUIRES_NEW最常见的场景就是日志记录，比如业务和日志在同一个事务里，业务操作失败回滚了，日志也会回滚，用REQUIRES_NEW，日志写在新事务里，业务回滚不影响日志。

# 前提：有两个bean的类，UserController和UserServiceImpl实现类，UserController注入UserServiceImpl实现类，UserServiceImpl实现类有两个方法，a和b，UserController去调用UserServiceImpl实现类的a方法，并且a方法中调用了b方法，第一个问题：a方法没有加@Transactional，b方法加了@Transactional，b方法的事务会生效吗？第二个问题：a和b不在同一个bean了，然后a和b方法都加了@Transactional，b抛出异常了，a方法用try-catch捕获了b方法抛出的异常之后就没有再往上抛出异常了，a方法会回滚吗？

不生效，Controller调用的是代理对象的a方法，a方法没加事务，直接走原始对象的a，然后a里面调b是自己调自己，绕过了代理，事务不生效。

要看情况，如果是默认的传播行为REQUIRED，虽然a捕获了异常，但b已经把共享事务标记为回滚，a也会回滚；如果b的传播行为是REQUIRES_NEW，a调b时a的事务会挂起，b会单独开一个事务，抛异常后b的事务会回滚，a不会回滚。

# 说一下mysql的存储引擎有哪些？说一下innodb和myisam的区别？存储引擎针对的是表还是数据库？

常见的有InnoDB、MyISAM、Memory。

InnoDB支持事务、外键还有行锁，并发高；

MyISAM不支持事务、而且只有表锁，写操作全串行，也不支持外键。

针对表，建表的时候可以指定，同一个数据库不同的表可以用不同的引擎。

# 什么是mvcc机制？

MVCC是多版本并发控制，解决读写之间的冲突。传统的做法是加锁，读不能写，写不能读。MVCC给每行数据存了历史版本，每个事务读自己该看到的版本。

具体实现就是InnoDB每行数据都有三个隐藏的字段，事务ID、回滚指针、隐式主键。修改一行数据前，会先把旧值写undo log里，多个undo log串成版本链。事务去读的时候会带着自己的Read View去到版本链里找，只能找已提交的。

读已提交就是每次查询都生成新的Read View，所以能看到别人刚提交的数据。

可重复读是事务开始就生成一个Read View，全程用这一个，所以数据始终一样。

# 说一下mysql的主从复制过程

主从复制就是主库把数据同步到从库，让数据保持一致，首先主库要开启binlog日志，主库有数据变更，先把sql写到binlog里，从库会启动一个IO线程连到主库，主库再开个dump线程把binlog的内容推给从库，从库IO线程收到后写到自己的relay log里；最后从库再启动一个sql线程，读relay log的内容，一条一条在自己库上执行，数据就同步过来了。

补充：IO线程和SQL线程分开是为了异步解耦，IO管收集，SQL管执行，互不影响，整体吞吐量高。

# mysql有哪些日志文件及它们的作用是什么？

binlog：记录所有数据变更的SQL，主从复制、数据恢复就靠它。

redo log：事务提交前先写redo log，记录每个位置改了什么内容，保证宕机后不丢数据。

undo log：记录数据旧值，回滚靠它恢复，MVCC靠它串成版本链。

slow log：记录超时查询的SQL，默认10秒。

relay log：相当于binlog在从库上的副本。

# mysql索引的底层数据结构是什么？为什么选择b+树，而不是二叉树、平衡二叉树、红黑树、b树？

MySQL索引默认用的是B+树。

二叉树极端情况会退化成链表，比如插入有序数据，二叉树就变成一根斜线，查询次数等于节点数。这时候时间复杂度会降为O（n）；

平衡二叉树和红黑树解决了退化问题，但本质上还是二叉树，一个节点只存一个数据，百万级数据磁盘IO扛不住。

B树是多路平衡树，一个节点能存多个数据，树的高度比二叉树低，但有两点核心缺陷：

B树的所有节点都会存储完整行数据，一页能存放的索引key变少，树高度会更高，磁盘IO次数变多；

B树叶子节点没有双向链表，做范围查询和分页查询的时候，需要来回向上回溯父节点，频繁产生磁盘IO，范围查询性能很差。

同时中间节点存数据也会导致节点更容易分裂，维护成本更高。

# 聚集索引和非聚集索引的区别

聚集索引的叶子节点直接存整行数据，一张表里只能有一个；InnoDB里，有主键就用主键做聚集索引，没主键就找第一个唯一索引，都没有就创建一个隐式主键。

非聚集索引的叶子节点存的是主键值；查完非聚集索引，还要拿着主键值去聚集索引再查一次，也就是回表。一张表可以有多个非聚集索引。

# mysql有哪些索引类型？

MySQL的索引按功能分常见的几种：

第一种主键索引：每张表只能有一个，唯一、不能为空，如果不主动创建，MySQL底层会帮我们创建一个隐式主键，但是性能会有一定的损耗。

补充：这个隐式主键是一个全局共享的自增计数器，高并发写入时所有没主键的表都会抢这个计数器，会有锁竞争，而且这个主键最多6个字节，用完就归零循环，可能会覆盖旧数据。

第二种唯一索引：不能重复，但是可以为null，属于二级索引，每张表可以有多个唯一索引。

第三种普通索引：也就是最基本的索引，没有约束，纯粹为了加速查询。

第四种联合索引：多列组成一个索引，遵循最左前缀原则——查询条件必须从索引的第一列开始匹配才生效。

# 什么是最左匹配原则？联合索引为什么要遵循最左匹配原则？什么是全表扫描？

最左匹配原则就是联合索引必须从最左列开始匹配，跳过最左边的列，直接用后面的列，索引就不生效。

因为B+树构建联合索引的时候，是按索引列顺序对树排序；如果跳过一个字段，B+树就不知道后面的字段在哪里，没法走索引。

全表扫描就是没走索引，MySQL把整张表从第一行扫到最后一行，数据量大了会炸。

# 按照abc顺序建立联合索引，下列情况会不会走索引，where a = 1 and b=1 and c=1、where b=1 and c=1 and a=1、where a = 1 and c=1、where b=1 and c=1、where a>1 and b=1、where a=1 and b>1

必须有最左列才走索引，只要有最左列在，MySQL会自动优化条件顺序，如果没有中间列，后面的列就不会走索引。

如果某一列是范围查询，后面的列都不会走索引。

# 建立索引一般要考虑什么？

一般只会针对频繁在连接、筛选、分组、排序中做条件的字段建立索引

首先要考虑表的大小，如果只有几十条数据，预知以后数据量也不大，可以不用建立索引

然后区分度低的列，比如性别，一半数据都一样，B+树分不出层次，扫一大片还要回表，不如全表扫描。但是如果确定女多男少或者男多女少，索引的效果就很好

索引是拿写的速度换读的速度，多个条件查就建联合索引比多次查单索引然后合并效率更高。

# 什么索引下推？

索引下推是MySQL5.6加入的回表优化，它会把属于索引的筛选，尽量放在索引树上就做完，假设有联合索引abc，执行a = 1 and c = 2的查询语句；

如果是5.6之前，MySQL在索引树找到100条a的记录，会回表100次去筛选符合c的记录。

有了索引下推后，在找到100条a的记录后，会直接在索引树看c的值，如果有5条符合，会跳过其他记录，只用回表5次。

# 什么是回表？怎么优化回表？什么是覆盖索引？

非聚集索引叶子节点只存主键值，没有整行数据，必须拿着主键去聚集索引再查一次，这就是回表。

优化回表最直接的方法就是select的字段全部命中同一颗索引树，直接返回。

或者利用索引下推在联合索引查询时，在索引树里把能过滤的条件都过滤掉，尽可能减少回表次数。

覆盖索引就是select的所有列都在同一棵索引树的叶子节点里。

# 索引失效有哪些场景？

最常见的就是联合索引查询没有最左边的列，因为B+树是按最左排序。

第二个是模糊查询如果以%开头，也会失效，因为B+树是字符顺序排列，不知道从哪开始找，只能扫全表。

然后条件查询如果把索引列套了函数，没办法直接和索引树的值匹配，也会失效。

还有条件查询值类型必须和索引列类型一样，比如电话号码如果不加引号，MySQL会把索引列隐式转换成数字一条一条对比。

# 深分页查询如何优化

深分页最常用的优化就是延迟关联，可以先只查主键，因为不用回表，然后拿主键去回表取数据，查几条就回表几次。

第二种是游标分页，记录上一页最后一条的id，直接跳到后面截取，缺点是不能跳页，而且要求排序字段是主键。

还有就是覆盖索引，不过业务中基本不可能覆盖。

# 有没有做过慢sql调优？

有做过，首先定位慢SQL，开启慢查询日志，得到慢SQL后用explain关键字进行分析，我主要关注重点字段：

第一：type有没有走索引

第二possible_key：可能会走的索引

第三key：实际使用的索引

第四key_len：联合索引命中长度

第五extra：查看有没有覆盖索引、创建临时表、额外排序

如果没有索引就新建；有索引但失效，就排查失效场景。

建立合适联合索引，利用覆盖索引减少回表；

统一使用InnoDB；字段类型能整形就不字符串，省空间；

尽量避免select *，只差需要字段；少多表联查；union all代替union，避免自动去重排序。

# 有没有做过数据库调优？

有做过，分四个层面：

第一层：最基础的SQL和索引，用explain分析执行计划，建合理的索引、排查索引失效、避免回表；

第二层：MySQL参数调优，最重要的就是缓冲池大小，InnoDB操作数据不是直接读磁盘，会先把数据页加载到内存，这块内存就是缓冲池，缓冲池数据越多磁盘IO就越少，默认是128M，生产环境一般按服务器内存的50%-70%去配。

第三层：架构层面，查询多写少就做读写分离，主库写从库读；数据量大到千万级考虑做分库分表，不过我目前项目里没实际做过，只是知道这个方向。

第四层：表结构设计，字段类型选对，避免建太多索引。

# 为什么mysql推荐使用自增数字作为主键？

因为InnoDB用的是聚集索引，数据按主键顺序存放，自增主键每次新数据一定比旧数据大，直接追加到最后；顺序写入速度快，空间利用率高。如果主键随机比如uuid，插入点可能在中间，频繁页分裂，碎片多，读写都慢。

另外二级索引叶子存的是主键值，用BIGINT只占8字节，用uuid占32甚至更多。
