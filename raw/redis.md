# redis为什么这么快？

有几个主要原因：

第一，Redis是纯内存操作，内存访问速度比磁盘快很多。

第二，它是单线程模型，避免了CPU上下文切换的开销。

第三，底层使用IO多路复用的同步非阻塞 NIO 接收请求，一个线程可以处理多个请求。

第四，底层有比较优化的数据结构。不是指 string、list 那五种常用数据类型，是指它们底层用 C 语言实现的数据结构。

# 说一下redis的常用数据类型及使用场景，string和hash都可以用来存储对象，什么时候选择string？什么时候选择hash？

Redis的常用类型有五种：

第一种String：最简单的键值对，计数器、分布式锁、存对象的 JSON 字符串都可以用它。

第二种Hash：类似一个对象，存一组关联字段，比如姓名、年龄、手机号存成一个Hash。

第三种List：有序列表，可重复，按插入顺序排，可以用来做消息队列。

第四种Set：无序集合，它是自动去重的；做交集并集很方便，比如共同好友。

第五种ZSet：带权重的有序集合，按score排序。排行榜用它最合适。

两个都能存对象，区别在访问模式上：

如果大部分时候是整存整取，像缓存用户登录的session、JWT token，就用String。

如果经常只读或者只改对象部分信息，比如用户资料只改了昵称，如果用String存json，要先把整个json取出来改昵称再整个塞回去，Hash可以直接Hset修改单个字段。

# 说一下redis的缓存淘汰策略

Redis的缓存淘汰策略有八种，分为三类：

第一类，noeviction，内存满了直接拒绝写请求，写会报错，但是读正常。

第二类，从所有key里淘汰：allkeys-lru淘汰最近最少用的，allkeys-lfu淘汰最不经常用的，allkeys-random随机淘汰。这三个不管key有没有设过期时间，内存满了就删。

第三类，从设置了过期时间的key里淘汰：volatile-lru，volatile-lfu，volatile-random，还有一个volatile-ttl淘汰最接近过期时间的。

# 说一下redis的过期策略

Redis用的是惰性删除和定期删除两种组合：

惰性删除是key到期后，等下次有人访问这个key才检查，发现过期了再删。

定期删除是Redis每隔一段时间随机抽查一批设置了过期时间的key，把其中过期的删掉。

两个互补：惰性删除省CPU，定期删除清内存。

补充：还有一个定时删除，是给每个key设一个定时器，到期立刻删，但是key多了会有一堆定时器吃CPU，不现实。

# 说一下redis有哪些持久化策略？

Redis有两种持久化策略，RDB和AOF，可以混合使用。

RDB是快照，每隔一段时间把内存数据全量写到磁盘。恢复快、文件小，但如果两次快照之间Redis挂了，这段时间的数据就丢了。

AOF是追加写日志，每执行一条写命令就记到AOF文件里。数据安全性高，最多丢一秒的数据，但AOF文件会越来越大，恢复速度也比RDB慢。Redis会定期对AOF文件做重写压缩，去掉冗余命令。

生产环境一般两种都开，RDB做全量备份，AOF保证增量不丢。

# 说一下缓存三兄弟（三剑客）分别造成的原因和解决方案

缓存三兄弟指的是缓存穿透、缓存击穿、和缓存雪崩。

首先缓存穿透是查一个不存在的数据，每次都查到数据库，原因一般是恶意攻击或者爬虫扫不存在的ID；解决方案我了解两种：

一是布隆过滤器：在缓存前面加一层，提前判断key存不存在，布隆过滤器说不存在直接返回。

还有一种就是数据库查不到就缓存一个空值，过期时间设短一点。

缓存击穿是一个热点数据刚好过期，大量请求同时进来，全打到数据库上；解决方案：

可以给热点数据不设TTL，存逻辑过期时间字段，查到过期先返回旧数据，再异步开一个线程去更新数据库和缓存。

也可以用互斥锁，每次只有一个线程去查数据库，其他线程排队。

还有缓存雪崩，原因是大量缓存在同一时间过期，或者Redis挂了，所有请求直接到数据库，这也是三兄弟最严重的；有三种解决方案：

第一种可以给每个key的过期时间加一个随机偏移，避免同时过期；

第二种用本地缓存+Redis，Redis挂了本地缓存还能扛一阵。

第三种用主从+哨兵或者集群模式，一个节点挂了另一个顶上来，保证整体不宕机。

# 项目中哪里用到了分布式锁？说一下分布式锁redisson的底层原理，说一下看门狗机制

主要是抢单场景，多个服务人员同时抢同一个订单，如果不加锁，可能两个人同时抢到。所以用分布式锁，同一个订单同一时间只有一个人能抢到锁，抢到的执行派单。

普通Redis分布式锁有个问题，锁过期了业务还没执行完，锁会自动释放，别人抢进去就会出并发问题。redisson就是在这基础上封装了一套完整的锁机制

底层是：

Lua脚本+Hash结构，锁在Redis里存的是一个Hash，key是锁名，filed是线程ID，value是重入次数；

加锁执行Lua脚本先判断锁存不存在，不存在就hincrby设为1；存在就判断是不是当前线程，是就重入次数+1，不是就返回剩余过期时间；

解锁时执行Lua脚本重入次数-1，如果减到0就删除这个key，同时发pub/sub通知等待的线程

看门狗机制默认加锁时锁的过期时间是30秒，业务还没结束，每隔十秒，看门狗线程会自动把锁续期到30秒。如果加锁时手动指定了时间看门狗不会启动，他会认为你自己管锁的时间。

# 项目中一般用redis来做什么？项目中具体是哪里用来做缓存？怎么保证数据库和缓存的一致性？

我们项目里Redis主要做两件事：

第一是缓存，有两个场景，一个是服务人员APP会实时上报GPS位置坐标存到Redis，派单匹配距离的时候直接读Redis。另一个是AI客服的会话上下文，用Redis存多轮对话记录，支持滑动窗口token长度。

第二是分布式锁，多个服务人员同时抢一个订单，用Redis的SETNX加锁保证只有一个人能抢到。数据库也加了唯一索引兜底，订单号+服务人员ID建唯一约束，极端情况下Redis锁失效了，数据库层面也能拦住重复派单。

我们用的是先更新数据库再删缓存。删缓存失败就发一条MQ消息后台重试删除，加上缓存本身有过期时间兜底，保证最终一致性。

之所以不用先删缓存再更新数据库，是因为删完之后更新之前，刚好有读请求进来，读到旧数据又写回缓存，缓存就一直是脏数据。

延迟双删也能解决，但两次删除之间的时间间隔不好控制。Redisson读写锁太重了，我们场景够用就没上。

# redis有哪些类型的集群？哨兵集群有什么作用？说一下什么是主观下线和客观下线？说一下分片集群相比哨兵集群有什么优点？你们公司用的是哨兵集群还是分片集群？

Redis集群有主从、哨兵、分片集群三种。

哨兵集群的作用就是监控主节点，主节点挂了自动选一个从节点升为主，不需要手动干预。

主观下线是单个哨兵觉得主节点挂了，可能是网络抖动误判。客观下线是超过一半的哨兵都认为主节点挂了，才会真正触发故障转移。

分片集群比哨兵的优势就是数据可以水平拆分，每个分片存一部分数据，不再受单机内存限制。而且单个分片挂了只影响那一小部分数据。

我们用的是主从模式，一主两从。主节点负责写，从节点分担读压力。数据量和并发还没到需要分片的程度，主从够用了。

# 什么是Redis的主从复制，主从复制的流程是什么？

主节点负责写，从节点负责读，分担读压力。

第一次同步是全量：从节点连上来，主节点生成RDB快照发给从节点，同时生成RDB期间的新写命令存在replication buffer里。从节点加载完RDB后，主节点会把buffer里的命令补发给从节点执行，这样主从数据就完整同步过来了。

之后都是增量同步：主节点每执行一条写命令都会发给从节点，从节点实时跟着执行。如果从节点掉线了又重连，就会上报自己的offset偏移量，主节点看看从节点落后了多少，把offset之后的命令补发过去就行，不用全量同步。

但如果从节点掉线太久，主节点的 repl backlog 已被新命令覆盖，找不到对应 offset，就只能再走一次全量同步。

# Redis集群脑裂是什么？怎么解决？

Redis集群脑裂通常是指在哨兵模式下发生网络分区，哨兵集群联系不上主节点，以为它挂了，就选了个新的主节点。但实际上旧主节点没挂，这时候就出现"双主"的情况；网络恢复后旧主会降成从节点，需要全量同步新主的数据，会先清空自身数据，导致之前双主期间写入的数据丢失。

解决可以配置两个参数，min-slaves-to-write设置主节点至少要有几个从节点才能写入，还有min-slaves-max-lag设置从节点延迟超过多少秒就拒绝写入。这样网络分区发生的时候旧主发现从节点丢了，会拒绝写入，这样就不会产生脏数据了。
