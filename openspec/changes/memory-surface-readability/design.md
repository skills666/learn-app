# Design

## Context

动机见 proposal.md - Why。这里只列约束当前做法的事实：

- 队列构建在 `buildMemoryQueue()`（d:\learn\learn-app\index.html L4609-4646），每条队列项已带 `overdue`、`level`、`isNew`、`docOrder`，并在构建期顺带算出 `queue.maxOverdue`（L4641）。**这套「构建期一次算好、渲染层只读」的做法是本页的既有约定**，本次新增的派生量必须沿用它。
- 派生量的共享口径目前有四个函数并列：`fsrsStateOf`（L2233，老数据换算）、`levelOf`（L2288，由 S 派生等级）、`effectiveNextOf`（L2307，掌握题到期时间）、`dayIndexOf`（L2460，自然日序号）。它们的注释都明确写着「记忆队列 / 总览统计 / 进度报表三处必须共用」，历史上分开写过导致过同题不同答。
- 记忆卡头部 pmeta 每次换题整块 `innerHTML` 重写（L5144-5149），而等级条走 `paintLvBar` 的段节点复用（L4653 注释）——**同一页面里两种更新策略并存，新增可视元素必须选对边**。
- 进度页数据行 `buildAnalyticsData`（L5195-5227）已经产出 `s` 与 `d`（L5219-5220 用 `fsrsStateOf`），并落到 CSV 与复制报告（L5241）。DSR 里只有 R 缺席。
- 冒烟测试用 `extractConst` / `extractFunction` 把源码片段抽进沙箱单跑：常量必须**单独成行声明**才可被抽出（L139-145 的既往说明），被抽的函数不能引用沙箱里没声明的标识符（L7887-7888 就是这个坑的登记）。另有直接匹配源码文本的静态断言（L836 等），改了被匹配的写法就得同步改断言。

## Goals / Non-Goals

**Goals:**

- 把调度器已算得出但从未显示的量（R、欠账构成）变成用户能读的界面信息。
- 让复习顺序承载「先救最不可靠的」这条意图。
- 新增的一切都能被 `npm run verify` 的既有三道门覆盖到。

**Non-Goals（设计层边界，比 proposal 更具体）:**

- 不引入任何"今天做多少"的状态机。没有配额计数器、没有剩余题的推迟逻辑、没有"明天继续"的语义。
- 不改 `overdue` 字段本身（只改它在排序里的**位置**），以免打断依赖它的行为断言与进度页口径。
- 不改云同步载荷：新增的展示标记键是**设备本地**的展示去重信息，与 `hot` / `warlog` 一样不进 `learn-data.json`。
- 不动答案折叠容器 `.rv-in` 的 overflow 语义（近期刚修过长串被裁的问题）。

## Decisions

### D1：新增 `retrievabilityOf(p, now)` 作为第五个共享口径函数

放在 `effectiveNextOf` 旁边（L2307 附近），签名与它一致，返回 `0~1` 的数值或 `null`。

```
retrievabilityOf(p, now):
  st = (p.fsrs && p.fsrs.s > 0) ? p.fsrs : fsrsStateOf(p, now)   // 与 levelOf L2292 同一分支
  if(!st) return null                                             // 从未评分 = 无数据
  elapsed = max(0, (now - (st.last || now)) / 86400000)
  return fsrsRetrievability(elapsed, st.s)
```

- **为什么单独成函数而不是在两个显示点各写一遍**：这正是 `effectiveNextOf` 存在的理由（三处口径分裂过一次）。展示层一旦分写，将来改公式必漏一处。
- **替代方案（已否）**：在 `levelOf` 里顺手返回 R。会让一个函数有两个出口，且 `levelOf` 被缓存增量路径（`bumpLvCounts`）依赖，改它风险面扩大。

### D2：R 的时间口径用真实经过时间，不采用自然日

与调度内部（L2247）完全一致。`overdue` 走 `dayIndexOf` 自然日是为了「欠几天」的整数语义，两者服务对象不同，**故意不统一**，并要在函数注释里写明这一点——否则后来者会"顺手统一"掉，然后出现「进度页说 R=88%、记忆页说还没到期」。

### D3：R 的分档阈值单独成行声明为常量

```
const R_GOOD_TH = 0.9;   // R 高于此值视为稳
const R_WARN_TH = 0.7;   // 低于此值视为基本凉了
```

- **为什么必须单独一行**：`extractConst` 按声明逐条取（见 L139 那段把 `MASTERED_MIN_DAYS`、`FSRS_MIN_STABILITY`、`SM2_INIT_EF` 分开的注释）。合在一行声明就抽不出来，冒烟会直接失败。
- **措辞**：界面显示整数百分比 + 分档语义色（`--good` / `--warn` / `--bad`，走令牌不写死色，遵循 L501 那条既有批评）；`—` 用于无数据。
- **替代方案（已否）**：只显示百分比不着色。少了一层"要不要现在刷它"的即时判断，而这正是本次的目的。

### D4：排序改为「新题 → R 升序 → overdue 降序 → level → docOrder」

替换 L4639 那条比较链的第二位，**保留 `overdue` 作为 R 相等时的次级 tie-break**，而不是删掉它。

- 为什么不新增第四优先级而是替换第二位：`overdue` 单独排序在「全库逾期」时几乎无区分度（大家都差 8~15 天），而 R 已经把"欠多久 + 记多牢"合成一个数。保留 `overdue` 只当平手裁决，既守住「顺序可复现」这条契约（`docOrder` 仍是最终稳定末位），也不销毁旧信息。
- 为什么 `isNew` 仍在最前：新题从没进过排期，越晚铺越迟回来，是既有语义，本次不动。
- **回滚成本**：这一条是一个表达式，不适应时改回一行即可。

### D5：欠账三段计数在构建期算（已作废，理由见 D9）

```
queue.seg = {d1to7, d8to14, d14plus}   // 挂在数组对象上，与既有的 queue.maxOverdue 同构
```

分段边界取 1~7 / 8~14 / >14：**7 = `FSRS_MAX_INTERVAL`**，超过一倍上限说明真的放凉了；不是随手取的数。

- **为什么不在渲染层算**：pmeta 每次换题都重写，逐次遍历千条队列是白烧（当初正是为此把 `maxOverdue` 挪进构建期）。
- `overdue === 0` 的题（今天到期）不计入三段，另给一个「今天到期」计数，否则三段之和与队列数对不上，用户会以为丢题。

### D6：回归说明态用「本周期是否已刷过题」判定（已作废，理由见 D9）

新增标记键 `learnAppReturnBrief_v1`，值写**展示当时的全库最大 `lastPracticed`**（无则为 0）。

```
展示条件 = queue.maxOverdue > 7 且  标记值 === 当前 maxLastPracticed
```

含义：展示过之后一题都没刷 → 不再唠叨；刷过任何一题（`maxLastPracticed` 变化）→ 进入新周期，若仍大面积逾期可再次展示。

- **为什么不用 `Date.now()` 存展示时刻**：改系统时间、跨时区、云端合并另一台设备的排期都会让判定失真；`lastPracticed` 是应用内已有且唯一可信的"用户动过"信号。
- **为什么不复用「今天」的日键**：停练可能发生在同一天内的几小时后，日键会把该展示的场景吞掉。
- **退化是良性的**：`safeLocalSet` 写失败（配额紧张）时返回 false 而不抛异常（L3303-3306），后果只是"下次进来又说明一次"，不影响数据与队列。

### D7：分段进度条按 20 等分（已作废，理由见 D9）

- 「每 50 道一格」在 120 题的队列上只有 2 格，在 2000 题上有 40 格，窄屏必溢出。固定 20 格则任何规模都是 5% 一格，视觉稳定，可用 `flex:1` 均分且无需媒体查询。
- 容器**独立于 pmeta**，挂在卡片区上方，按 `data-seg` 复用节点（照 `paintLvBar` 的思路），避免每换题重建 20 个节点。
- 精确数字仍保留在右侧（`3/1000` 不删，只是不再是唯一的进度线索）。
- **修订**：段条右侧的欠账构成文字（`.mp-txt` / `memSegText`）已取消，段条只表示进度。

### D8：进度页与 CSV 加一列 R

`buildAnalyticsData` 的 rows 加 `r`（与已有的 `s`/`d` 同源同一次 `fsrsStateOf` 调用，不多跑一遍换算）。导出 CSV 与复制报告同步增列。

### D9：用户实测后移除「回归说明屏」与「欠账三段计数」

用户在真数据（停练 16 天 / 253 题）上看过实际效果后判定两者无价值。这不是事前能推出来的——所以记录下来，以免下次再用同样的思路重做：

- **三段计数对行动零指示力**。「先刷哪个」已经由 D4 的 R 升序排序做完，三段只是在解释系统怎么想的。决断量与解释量同时存在时，用户只读得进去前者。
- **说明屏四行里只有一句有信息量**（停了多少天、多少题到期），而这句卡片头部「🕒 队列最久欠 N 天」已经给了。剩下的「这不是欠两个月的债」（自我安慰）、「按概率排序」（实现细节）、「做完多少算多少」（承诺）都不需要一块整屏来承载。
- **`queue.seg` 随之成为死代码**：它的两个消费者都没了。按本文件一贯的「同一件事只存一处」原则，派生量与它的构建遍历、计数断言一并删除，不留"以后可能用得上"的死代码。
- **总览等式额外带出一个布局回归**：`.ov-grid{grid-template-columns:repeat(5,1fr)}` 是 grid，同行卡片默认等高——单张卡多一行文字会把整排（包括保留率卡）顶高。这属于本次改动里少数真正的实现缺陷，不是审美问题。往总览卡里加行之前，先看它会不会抬高同一 grid 行的邻居。
- **保留什么**：R 显示、R 排序、总览上「到期 / 未学」两个数字同权重并排（只删等式文字）。后者是用户最初误读的解药，不能跟着等式一起砍。
- **第二轮又删了 20 格分段进度条**（用户实测后指出，当时被当成"没删干净的残留"）：它跟一直存在的等级分布条 `.pbar.lvbar` 形状相同、语义完全不同（一个是"库熟到什么程度"，一个是"本轮走到哪"），上下相邻就是重复。实测堆叠：`lvbar h=10` → `pmeta h=19` → `mem-prog h=6` → 卡片。**教训：往一个已有同类元素的区域再加一条同形状横带前，先看它会不会被读成重复或残留**；而"千题规模才需要进度分段"这个前提在用户当前规模下并不成立，属于提前优化。

## Risks / Trade-offs
- **[改排序会让"撤销后定位"看起来怪]** 撤销用 `findIndex(qid)` 定位（L4740-4742），不依赖顺序假设，逻辑安全；但用户可能发现撤销后跳到的题在队列里的位置和记忆不一致 → **缓解**：撤销栈存的是 qid 与快照，与顺序无关；补一条行为断言「撤销后仍定位到被撤销的那道题」。
- **[全库低 R 时界面一片警示色，读起来像被责备]** → **缓解**：R 的语义色只在答案展开后（评分时机）出现在卡片头部；未展开时不给颜色，只给数字；同时按 proposal 把 `maxOverdue > 7` 的告警色降为中性。
- **[CSV 列序变化可能影响用户自己的外部脚本]** → **缓解**：R 追加在现有列之后而不是中间插入，并在 tasks 里列为需要显式告知的一次格式变更。
- **[静态断言与源码文本耦合]** 改动 `renderMemory` / `buildMemoryQueue` 写法时，若撞到 d:\learn\learn-app\scripts\smoke-test.js 里匹配源码的静态断言，必须同一提交里同步改断言，不能只改一处。
- **[性能]** 构建期多出一次 O(n) 派生（R 与三段计数），与既有 O(n) 遍历同轮完成，不新增全量遍历；千题量级下可忽略。
- **[Trade-off]** 队列不裁剪意味着长期停练后一次面对全库。这是用户明确要的（「排期来了有多少就刷多少」），本次通过"排序 + 说明"降低其心理成本，不通过减少题量。

## Migration Plan

1. 单文件改动：新增 `retrievabilityOf` 与两个阈值常量 → 队列构建加派生量 → 排序 → 头部与段条显示 → 回归说明态 → 进度页加列。
2. 补冒烟：`retrievabilityOf` 函数级断言、队列排序与三段计数行为断言、回归态渲染断言（render-smoke）。
3. 版本号双写：`index.html` 的 `SW_VERSION` 与 `sw.js` 的 `CACHE` 同轮递增。
4. 验证：`npm run verify`（check + 两个冒烟）。
5. **回滚**：无数据结构变更、无迁移写入，`git revert` 单文件即可；标记键留在本地不影响任何行为（读不到即按"未展示过"处理）。
