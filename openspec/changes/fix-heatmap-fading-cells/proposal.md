# Proposal

## Why

进度页热力图的色阶来自 [`hmDayCounts()`](file:///d:/learn/learn-app/index.html#L5289-L5300)，它按每道题 `PROGRESS[q].lastPracticed` 归日（L5293-5297）。`lastPracticed` 是**每题一个、会被覆盖**的字段，所以一道题在任何时刻只给一格上色——给它最后被练的那天。结果：一旦那天的题后续又被练过，颜色就被搬走，那格归零变回默认色。**亮过的格子会熄灭，不是偶发故障，而是这个数据源的定义。**

而 `FSRS_MAX_INTERVAL = 7` 让这件事变得绝对：任何题最多 7 天必然回到队列，必然把它的 `lastPracticed` 搬走。所以这张图实际只能显示最近约 7 天，图注却写着「今年 1/1~12/31」（L5284）——**全年视图配了一个只有约一周记忆的数据源**。

同一个字段还喂着连续打卡：`computeAllStats` 的 `reviewed` 集合同样从 `lastPracticed` 建（L3354-3356），streak 靠逐日回查（L3373-3379）。因此**连续天数的天花板被排期上限钉死在约 7 天**，一天不落刷满一年也显示不出「连续 30 天」。L3375 那条注释说把循环上限从 365 提到 3650 是为了不让满年用户恒定显示 365——那次改动没触到真问题。

[L5281-5283](file:///d:/learn/learn-app/index.html#L5281-L5283) 的注释承认口径不精确，但把「不精确」推成了「现有数据完全够用」，这一步跳错了：「当天推进过的题量」这个量本身不守恒，一次重刷就从旧日期抽走，所以它根本回答不了「哪天在学」。

## What Changes

- **打卡事实改由「按日累计、只增」的记录提供**：热力图色阶与连续天数都换读按日累计的打卡记录（现有 WARLOG 就是它——只增、已按设备分层合并），不再从 `lastPracticed` 分布反推。
- **保留期拆成两个语义、两个常量**：逐题清单保留期（`WARLOG_QID_KEEP = 45`，只决定当天是否还留着逐题清单 `q`）与**打卡保留期**（`WARLOG_CHECKIN_KEEP = 370`，覆盖当前年度视图最长 366 天，决定颜色与回看能活多久）。超出前者只折叠掉 `q`，**四档计数、题数与首刷/升降级计数全部保留**。
- **回看不收窄**（更正前一版的误读）：热力图上任何有记录的日期都照旧可以点开看明细、开战报入口。所谓「不可回看」指的是**不跨年**——去年及更早的日子既不显示也不再保留。
- **因此老日子必须仍能供出数字**：`warDayAgg` 的覆盖题数加一条回退——`q` 不在时用折叠计数 `qn`，否则老格子会显示「复习 0 题」而变得可点却空（`q` 的唯一读取方就是这里，L2518-2519）。代价：`qn` 跨设备相加无法去重，超过 45 天的「覆盖题数」是**上界估计**，明细文案对这类日子改用「约 N 题」。
- **撤销不回退打卡**：撤销一次评分回退四档计数与数字，但**不把那天从"打过卡"变成"没打卡"**——那天确实做过这件事。与 L2616 既有的「`d.q` 不回收，宁可多算也不漏」同调。
- **打卡落盘加防抖**：`warLogAdd` 现在每次评分都 `JSON.stringify` 整份 WARLOG 并同步写（L2603），进度那边却有 600ms 防抖。保留期拉长后这个开销同步放大，必须复用既有防抖模式，并把打卡记录加进页面隐藏/卸载时的强制 flush 名单（L4050-4052 已有那套）。
- **修正两处错误注释**：L5281-5283 的「够用」论证、L3375 关于 3650 上限的理由说明。

**明确不做**：不跨年保留与显示（去年及更早的日子不显示、也不占存储）；不为老日期保留逐题清单；不重标定色阶阈值 `hmLvOf`。

**做不到、必须先说清的**：**已经熄灭的日子救不回来**。`warLogTrim`（L2527-2531）对超过 45 天的桶是真 `delete`，历史已不存在；而 `lastPracticed` 搬运丢掉的那部分也无法反推。本 change 只保证**从今天起**不再丢打卡事实，今年已过日子里的空缺不会补齐。

## Capabilities

### New Capabilities

- `stats-presentation`：约束学习统计量（打卡记录、连续天数、热力图与到期预测等）如何取数与呈现。本 change 往里加打卡相关的四条要求。

> 协调说明：change `overview-forecast-clarity` 也声明了这个 capability 并往里加要求（待复习/未学分列、到期预测分桶与峰值）。两份 delta 都带 `## Purpose`，先归档的一方建主 spec 文件、后归档的一方追加要求，任意先后都能归档。

### Modified Capabilities

（无——本 change 不改排期行为，`memory-scheduling` 不受影响）

## Impact

- **代码**：d:\learn\learn-app\index.html 内五处——`hmDayCounts`（L5289-5300，换数据源）、`computeAllStats` 的 `reviewed`/streak（L3354-3356、L3369-3380）、`WARLOG_KEEP` 与 `warLogTrim`（L2443、L2527-2531）、`warLogAdd` 落盘（L2603）与 `warLogUndo`（L2616-2620，明确不回退打卡）、`hmDayDetail` 与 `warEntryKey`（L5309-5332，回看能力**保持不变**，只对已无逐题清单的日子把「复习 N 题」改标「复习约 N 题」）。`warDayAgg` 加 `qn` 回退（L2518-2523）。
- **打卡语义的一处真实变化**：`warLogAdd` 唯一调用点是记忆模式评分（L2361），而 `lastPracticed` 也会被刷题模式翻页写入（L2595-2596 的注释就是这么说的）。换源后**「只翻题、没评分」的日子不再算打卡**，热力图在这一点上会比现在更空也更诚实。design.md 里给了一个一行的开关（要不要把浏览日也算打卡），默认不采纳。
- **存储与同步**：打卡桶保留到约一年。粗估（经验值，非实测）：折叠后的桶每条约几十字节，一年 365 条 ≈ 数十 KB，可接受；真正的大头仍是近 45 天带 `q` 数组的完整桶。WARLOG 每次推送都整包带上（Gist 更新未提及的文件会被删），保留期变长意味着载荷线性变大——这是接受折叠方案后唯一持续存在的成本。
- **测试**：d:\learn\learn-app\scripts\smoke-test.js 需要新断言组（重刷后老日期不变暗、撤销后打卡仍在、`qn` 回退、超期桶不产明细），并需要更新既有那条依赖 `hmDayCounts` 口径的断言；d:\learn\learn-app\scripts\render-smoke.js 里 `hmDayCounts` 的可用性断言（L327）要跟着改期望。
- **版本号双写**：`index.html` 的 `SW_VERSION` 与 `sw.js` 的 `CACHE` 必须同步递增。
- **不受影响**：排期与队列、云同步的合并语义（逐设备按 `at` 取新）、战报的数字口径。
